## 第 0 节 · 使用说明与 2026 年考情变化

**🔴 必考认知：2026 年的考点已经从「背概念」转向「讲闭环」。**

过去背一背 Transformer 结构、注意力公式、几个 RAG 名词就能过一面；现在面试官更愿意追问：
- 一个 Agent 如何在真实业务里**稳定运行**（异常、超时、重试、降级、人在环路）
- 如何**控制成本**（token 治理、模型分级路由、缓存、语义缓存）
- 如何**评估效果**（评测集怎么建、指标怎么定义、离线指标涨了线上为什么掉）
- 如何**定位线上问题**（可观测性、trace、回放）

## 第 1 节 · LLM 基础

> 面试出现率：**100%**（几乎每场都问，通常 10–20 分钟）
> 高频公司：所有（字节、百度、美团、阿里必问自注意力 + RoPE + KV Cache）

### 1.1 🔴 必考：自注意力（Self-Attention）原理与复杂度

**Q：讲一下自注意力机制，为什么复杂度是 O(n²)？**

- 输入序列每个 token 的向量先线性映射为 **Query / Key / Value** 三组向量。
- 用 `Attention(Q,K,V) = softmax(QKᵀ / √d_k) V` 计算：`QKᵀ` 得到 n×n 的两两相似度矩阵，softmax 归一化成权重，再对 V 加权求和。
- O(n²) 的来源很朴素：长度为 n 的序列里，**每个 token 都要和其余 n 个 token 算相关性**，于是产生 n×n 的注意力矩阵；时间和空间复杂度都是 O(n²·d)。
- 长上下文推理慢、显存高的根源就在这里，所以才有 FlashAttention、滑动窗口注意力、稀疏注意力、线性注意力这些优化。
- **为什么除以 √d_k**：点积的方差随维度 d_k 线性增长，数值过大会把 softmax 推到饱和区（梯度趋近 0），除以 √d_k 把方差拉回 1 量级，稳定梯度。
- **🟡 加分**：FlashAttention 不改变数学结果，只是通过 tiling 分块把中间矩阵留在 SRAM，减少 HBM 读写，把 IO 复杂度从 O(n²) 降到 O(n²/B)。

**Q：多头注意力（MHA）比单头好在哪？**

- 单头只能学到**一种**注意力模式；多头把 d_model 切成 h 份，各自在不同的子空间里关注不同关系（语法依赖、指代、远距离关联）。
- 最后 concat 再过一个输出投影 `W_O` 融合。
- **🟡 加分**：MHA → MQA（Multi-Query Attention，所有头共享一组 KV）→ GQA（Grouped-Query Attention，分组共享）演进的主线是**省 KV Cache 显存**，不是省参数量。LLaMA-2 70B 用 GQA，是为了在推理时把 KV Cache 缩小到 MHA 的 1/8 左右。

参考：[百度大模型算法岗一二面面经（牛客）](https://www.nowcoder.com/feed/main/detail/0024a4c85440443aacbda5f101c601a7)

### 1.2 🔴 必考：KV Cache 与显存估算

**Q：什么是 KV Cache？为什么它决定推理成本？**

- 自回归生成时，生成第 t 个 token 需要用到前 t−1 个 token 的 K 和 V。如果每步重算，整体是 O(n²) 的重复计算。
- KV Cache 把各层历史 token 的 K、V 缓存下来，**每步只算新 token 的 Q**，再与缓存拼接做注意力。把「重复做老题」变成「只算新增部分」，吞吐和延迟大幅改善。
- **代价是显存**：上下文越长、batch 越大、并发越高，KV Cache 越大，线上推理调度往往就被它卡住。
- **显存公式**（必背）：
  ```
  KV Cache 显存 = 2 × L × n_kv_heads × d_head × seq_len × batch × bytes_per_element
  ```
  - `2` 是 K 和 V 两份；`L` 是层数；`n_kv_heads × d_head` 等价于 KV 的总维度；`bytes` 是精度（FP16 = 2，INT8 = 1）。
  - 简写版：`2 × L × d_model_kv × seq_len × batch × bytes`
- **算例（务必能现场算）**：LLaMA-2 70B，L=80 层，KV 维度 8192（GQA 分组后每层 KV 实际维度远小于 8192，这里按 MHA 口径演示），FP16：
  `2 × 80 × 8192 × 4096 × 1 × 2 B ≈ 10.7 GB` —— 单条 4K 上下文就要 10 GB 级别的 KV Cache，这就是长上下文贵的真正原因。
- **算例 2（贴近实习场景）**：Qwen2.5-7B，L=28，GQA 下 n_kv_heads=4，d_head=128，FP16：
  每 token 每层 KV = 2 × 4 × 128 × 2 B = 2 KB；28 层 = 56 KB/token；8K 上下文 ≈ **0.45 GB**；并发 32 条约 **14 GB**。
- **优化方向（按收益排序）**：GQA/MQA → PagedAttention 消除碎片 → 量化 KV Cache（INT8/FP8）→ Prefix Caching（共享 system prompt 前缀）→ 滑动窗口/稀疏注意力。
- **权重显存估算**：`参数量 × 精度字节数`。7B FP16 ≈ 14 GB，7B INT4 ≈ 3.5 GB，70B FP16 ≈ 140 GB。**别忘了还要给 KV Cache、激活值和 CUDA 上下文留空间**，经验上单卡部署 7B FP16 至少要 24 GB 显存才舒服（推理框架本身还要 1–2 GB）。

参考：[27届大模型岗面试准备：推理加速全解——KV Cache、PagedAttention 与 vLLM（CSDN）](https://blog.csdn.net/thesky123456/article/details/163290783)、[大模型推理优化笔记](https://raw.githubusercontent.com/hqc135/personal-knowledge-assistant1/refs/heads/master/notes/llm-inference-optimization.md)

### 1.3 🔴 必考：位置编码（RoPE / ALiBi / 绝对位置编码）

**Q：讲一下 RoPE，它和绝对位置编码的区别？**

- **绝对位置编码（sin/cos）**：`PE(pos, 2i) = sin(pos / 10000^(2i/d))`，`PE(pos, 2i+1) = cos(pos / 10000^(2i/d))`，直接加到输入 embedding 上。缺点：外推能力差（超过训练长度性能断崖），位置信息是"加"进去的，会与语义向量纠缠。
- **RoPE（Rotary Position Embedding，旋转位置编码）**：不加法，而是对 Q、K 向量按位置做**旋转**。把向量按两两分组，第 i 组旋转角度 `θ_i = pos / 10000^(2i/d)`，用二维旋转矩阵作用：
  ```
  q' = q·cos(mθ) + rotate_half(q)·sin(mθ)
  ```
  核心性质：**两个旋转后向量的内积只依赖相对位置 (m−n)**，所以 RoPE 天然编码相对位置，且可以只在 Q/K 上做，不额外增加参数。
- **外推扩展**：直接外推会掉点，常见做法有 **位置插值 PI**（把超长位置压缩回训练范围）、**NTK-aware 缩放**、**YaRN**。这是面试加分点。
- **ALiBi（Attention with Linear Biases）**：不加位置编码，而是直接在注意力分数上加一个与距离成正比的负偏置 `−m·|i−j|`，越远惩罚越大。优点是零训练成本就能外推，缺点是相对"粗暴"，长文理解质量不如 RoPE 系。
- **🟡 加分**：面试常让你**手撕 RoPE**（见第 6 节），务必能写出来。

**Q：为什么现在的 LLM 大多用 RMSNorm + Pre-Norm？**

- **Pre-Norm**：把归一化放在子层**之前**（`x + Sublayer(Norm(x))`），残差路径上无归一化，梯度可以直接流过，训练更稳定，深层网络不需要 warmup 也能训。
- **RMSNorm**：去掉 LayerNorm 的均值中心化，只用均方根：`RMSNorm(x) = x / sqrt(mean(x²) + ε) · γ`。少一次减法、少一个 β 参数，速度更快，效果基本不降。LLaMA 系全用这个。

### 1.4 🔴 必考：Tokenizer（BPE / SentencePiece）与温度、top-p

**Q：BPE 是怎么工作的？为什么能缓解 OOV？**

- BPE（Byte Pair Encoding）的思想是「子词」：词级词表太大，字符级序列太长，取中间。
- **训练**：把文本拆成最小单元（字节或字符），反复统计出现频率最高的相邻符号对，把它们合并成新 token 加入词表，重复到达到目标词表大小（一般 3 万–15 万）。
- **编码**：按词表中**最长匹配**原则切分输入。
- **为什么缓解 OOV**：即使一个完整词没见过，也能退化成若干子词甚至字节表示，而不是变成 `[UNK]`。对多语言、拼写错误、长尾术语、emoji、代码都更鲁棒。
- **🟡 加分**：字节级 BPE（如 GPT 系、Qwen）对中文/emoji/URL 的适配优于字符级；SentencePiece 直接在原始文本上做，不依赖预分词，对中文、日文这类无空格语言更友好。
- **🟡 加分（百度常问）**：给代码补全 Agent 做 tokenizer 会遇到什么问题？——代码缩进/换行的 token 化不一致、标识符被切碎导致模型难以识别长变量名、不同语言混排、token 效率低导致有效上下文变短。优化方向：扩词表加领域 token、保留空白字符语义、对标识符做特殊处理。

参考：[百度大模型算法岗一二面面经（牛客）](https://www.nowcoder.com/feed/main/detail/0024a4c85440443aacbda5f101c601a7)

**Q：temperature、top-k、top-p 分别是什么？**

- **temperature**：作用于 logits，`p_i = softmax(z_i / T)`。T < 1 分布更尖锐 → 更确定、更保守；T > 1 更平坦 → 更发散、更有创意。T → 0 等价于贪心解码。
- **top-k**：每步只在概率最高的 k 个 token 里采样，固定候选数，问题是 k 固定不随分布形状自适应。
- **top-p（nucleus sampling）**：按概率从高到低累加，取累计概率刚好超过 p 的**最小集合**再采样。分布尖锐时候选少，分布平坦时候选多，更自适应。
- **工程参数经验**：严肃问答 / 代码 / 结构化输出 → `T=0~0.3, top_p=0.1~0.5`；创意写作 / 头脑风暴 → `T=0.7~1.0, top_p=0.9`。
- **🔴 关键认知**：这些参数改的是**解码策略**，不是模型知识。基础答案错了，怎么调采样都救不回来。面试官问「模型答错了怎么调 temperature」时要明确拒绝这个前提。

### 1.5 🔴 必考：上下文窗口、长文本处理、Lost in the Middle

**Q：上下文窗口是什么？超了怎么办？窗口大是不是就不需要 RAG 了？**

- 上下文窗口 = 一次前向计算能同时「看到」的 token 上限，包含 System Prompt、历史对话、RAG 检索结果、工具返回值和待生成内容。
- 超出后：API 直接报错，或框架自动截断（通常是静默截断开头，最危险）。
- **即使没超，也会「注意力稀释」**：这就是 **Lost in the Middle** 现象 —— 关键信息放在长上下文的中间位置时，模型召回率显著低于放在开头或结尾。所以不是拼命塞满窗口，而是**精准控制里面放什么**。
- **「上下文腐化」（context rot）**：多轮对话里早期内容虽在窗口内，但被后续大量内容稀释，模型对它的注意力大幅下降。
- **长文本工程手段**：滑动窗口（只留最近 N 轮）、对话摘要（模型压缩早期历史）、关键信息提取（把约束条件/用户偏好单独存，每轮注入）、RAG 外挂（按需检索而非全塞）、分层记忆。
- **🟡 加分回答**：窗口大 ≠ 记忆好。长上下文模型在超长输入上的有效利用率（effective context length）通常远低于标称值，且成本和延迟是平方级的。所以长窗口和 RAG 是互补而非替代。

### 1.6 🔴 必考：幻觉的成因与缓解

**Q：幻觉是怎么产生的？有哪些缓解方法？**

- **成因**：LLM 本质是「预测下一个最可能 token」的**概率生成器**，不是事实数据库。它优化的是语言流畅性，而非事实正确性；训练数据里的噪声和长尾知识稀疏也会导致编造。
- **缓解五板斧（按优先级）**：
  1. **RAG**：把真实资料塞进上下文，让模型基于证据回答 —— 这是最有效的手段。
  2. **Function Calling**：让模型调真实接口查数据（天气、订单、库存），而不是凭记忆编。
  3. **Structured Output + JSON Schema**：格式约束越强，模型自由发挥空间越小。
  4. **Prompt 明确拒答**：「如果资料中没有相关信息，直接回答『资料中未提及』」，虽不 100% 有效但显著降低编造率。
  5. **多轮验证 / 交叉校验**：让模型自查，或用另一个模型做 fact-check；关键场景加引用（citation）要求，答案必须能追溯到原文片段。
- **实际项目里一定是组合使用**，单点手段无法彻底解决。
- **🔴 高分点**：要能区分「检索侧幻觉」和「生成侧幻觉」—— 前者是没检索到/排错了，后者是检索到了但模型没忠实使用（Faithfulness 低）。**修复路径完全不同**（前者改 chunk/embedding/rerank，后者改 prompt/模型/上下文压缩）。只回答"换个更强的模型"是成本解，不是工程解。

### 1.7 🔴 必考：微调 vs RAG vs 提示工程的取舍

**Q：什么时候用微调，什么时候用 RAG，什么时候改 Prompt？**

- **一句话判据**：**让模型「知道新知识」用 RAG；让模型「学会新行为」用微调；让模型「按格式输出」先试 Prompt。**
- **RAG**：不改模型，改文档即可实时生效，成本低、可追溯、可权限控制。适合知识库问答、文档检索、时效性内容。
- **Prompt Engineering**：零成本、最快验证。适合格式对齐（few-shot）、角色设定（system prompt）、推理引导（CoT）。不稳定，模型换版本可能失效。
- **微调（SFT/LoRA）**：改变模型行为模式，需要 GPU + 高质量标注数据，成本高。适合：特定风格的输出、领域推理模式、**需要在各种输入下都稳定的格式/推理链路**（这是 RAG 做不到的，RAG 只能提供参考资料，不能保证模型按你想要的"方式"思考）。
- **🔴 高频追问**：什么是「必须微调」的场景？—— 你希望模型输出某种特定格式和推理链路，且这个模式要在各种输入下都稳定不变。
- **🟡 加分（SFT vs RLHF）**：SFT 适合快速迭代（流程简单，准备问答对即可，几小时到一天出结果）；RLHF 需要先训 Reward Model 再 PPO，链路长、工程复杂、稳定性差，但能学到「什么是好的」而非只是模仿数据里的模式。基模越来越强时，**SFT 的破局点是数据质量而非数量**（几百条高质量 > 几万条普通数据），**RLHF 的破局点是从人工标注走向可验证奖励（Verifiable Reward）**。

### 1.8 🟡 加分：主流开源模型与架构选型

**Q：了解哪些开源大模型？Qwen / DeepSeek / Llama 各自特点？**

- **Qwen 系列（阿里）**：Qwen2.5 / Qwen3 覆盖 0.5B–72B 密集 + MoE 版本，中文能力强、生态完善（有 coder / VL / audio 多条线），是国内私有化部署的首选之一。Qwen3 引入 thinking / non-thinking 双模式切换。
- **DeepSeek**：V3 是 MoE 架构（671B 总参数 / 37B 激活），R1 是推理模型，训练流程用 GRPO 做 RL。**🟡 面试常问 GRPO**：去掉 PPO 里的 Value Model（Critic），用**同一 prompt 采样一组（group）输出**，以组内平均 reward 作为 baseline 算 advantage，大幅降低显存和训练复杂度。
- **Llama 系列（Meta）**：Llama-3 用 GQA + RoPE + RMSNorm + SwiGLU 的标准 decoder-only 组合，是很多中文模型的架构蓝本。
- **🟡 MoE（Mixture of Experts）**：用 Router 为每个 token 选 top-k 个专家，总参数大但激活参数少，实现「大容量、低算力」。代价是显存占用大（要装下所有专家）、负载均衡难（需要 aux loss 或 bias 调节）、通信开销高（需要 Expert Parallelism）。
- **🟡 MHA / MQA / GQA 对比（百度二面原题）**：MHA 效果最好但 KV Cache 最大；MQA 最省（KV 只有 1 组）但可能掉点；GQA 是折中，把 h 个头分成 g 组，每组共享一组 KV，LLaMA-2 70B / Qwen2.5 都用它。**推理速度和显存占用的排序**：MQA > GQA > MHA（越靠左越省）。

## 第 2 节 · Agent 核心

> 面试出现率：**95%+**（Agent 岗必问，通常 20–30 分钟，且会围绕你的项目连环追问）
> 高频公司：字节、阿里、蚂蚁、小红书、腾讯

### 2.1 🔴 必考：什么是 Agent？和 Chatbot、普通 LLM 应用的区别

**Q：什么是 AI Agent？它和传统 Chatbot 的本质区别是什么？**

- **Chatbot 是被动的**：你问一句，它答一句，没有目标、没有状态、不能操作外部世界。
- **Agent 是主动的**：给定一个目标，它能**自主规划步骤、调用工具、观察结果、判断是否完成**，未完成就继续循环。
- **一句话公式**：`Agent = LLM（推理）+ Tools（行动能力）+ Memory（状态）+ Loop（自主迭代）`。
- 四个核心特性：**自主性（Autonomy）、目标导向（Goal-directed）、工具调用（Tool Use）、反馈适应（Adaptive to feedback）**。
- **五大核心模块**：任务解析（Task Parsing）、规划与推理（Planning & Reasoning）、工具调用（Tool Calling）、记忆管理（Memory）、执行与反馈（Execution & Feedback）。
- **🔴 关键区分点**：普通 LLM 应用是「一次调用得到答案」，Agent 是「模型自己决定下一步做什么，不需要人逐步指挥」。

参考：[AI Agent 面试问题集（GitHub）](https://github.com/kakaCat/langchain-learn/blob/main/AI_Agent_Interview_Questions.md)

### 2.2 🔴 必考：ReAct 范式（Reasoning + Acting）

**Q：什么是 ReAct？它怎么工作？请描述循环过程。**

- ReAct = **Reasoning + Acting**，核心是让模型在文本里**显式交替**输出三段：`Thought`（推理，为什么这么做 / 下一步选什么）、`Action`（调用哪个工具、什么参数）、`Observation`（工具返回结果）。
- 循环：`Thought → Action → Observation → Thought → …`，直到模型输出 `Final Answer`。
- **为什么要显式写 Thought**：① 可解释性（人类可审计）；② 可调试性（定位哪一步选错工具）；③ 学习信号（可做监督微调，或评估中间步骤质量）；④ 帮助模型在下一步更稳定地选 Action。
- **🔴 工程铁律**：**Observation 必须由执行器（工具/环境）生成，绝不能由模型自己续写**。否则模型会伪造证据，产生"看起来合理但错误"的答案。工程上要做好解析 + 校验 + 重试。
- **优缺点**：优点是接地（grounded）、可解释、工具解耦；缺点是每步一次 LLM 调用（成本延迟随步数涨）、**格式脆弱**（模型偏离模板就解析失败）、**逐步贪心缺乏全局规划**（复杂任务上不如 Plan-and-Execute）。
- **停止条件（❌ 只答"模型说完成就结束"是减分项）**：至少要有四种 —— ① 模型输出 Final Answer；② 达到 `max_iterations`；③ 检测到重复无效动作（相同工具 + 相同参数连续出现）；④ 出现不可恢复错误。生产环境还要加 ⑤ 达到 token / 费用预算上限；⑥ 用户中断。

参考：[AI Agent 面试八股文 · 核心框架（GitHub）](https://github.com/bcefghj/ai-agent-interview-guide/blob/main/docs/01-%E9%9D%A2%E8%AF%95%E5%85%AB%E8%82%A1%E6%96%87/02-%E6%A0%B8%E5%BF%83%E6%A1%86%E6%9E%B6.md)、[字节跳动 Agent 开发四面面经](https://programmercarl.com/)

### 2.3 🔴 必考：ReAct 与 CoT 的区别

**Q：ReAct 和 Chain-of-Thought 有什么本质区别？**

| 维度 | CoT（Chain-of-Thought） | ReAct（Reasoning + Acting） |
|---|---|---|
| 是否有外部环境 | 通常无，闭卷推理 | 有，工具 + Observation 反馈 |
| 输出内容 | 纯推理链文字 | Thought + Action + Observation 交替 |
| 纠错来源 | 主要靠模型自省 | 主要靠**外部真实反馈** |
| 典型目标 | 提升推理深度 | 推理 + 行动闭环 |
| 幻觉风险 | 高（凭记忆编事实） | 低（有工具结果锚定） |

- **一句话总结**：CoT 让模型「更会想」；ReAct 让模型「在想的同时能动手，并用真实结果纠正自己」。
- **🟡 加分**：CoT 是 ReAct 的**子集**（ReAct 的 Thought 部分就是 CoT），二者不是竞争关系。工程上常把 CoT 嵌进 ReAct 的 Thought 里，或用 CoT 做任务分解（Plan-and-Execute 的 Planner 阶段）。

### 2.4 🔴 必考：Plan-and-Execute 与 Reflexion

**Q：Plan-and-Execute 和 ReAct 什么区别？什么时候用哪个？**

- **Plan-and-Execute 是两阶段**：先由 Planner 输出结构化计划 `P = [step1, step2, …]`（每步含子目标、依赖、所需工具），再由 Executor 逐步执行并更新 state；失败或信息不足时触发 **Re-planning**（局部修复优先，全局重规划成本高但更稳）。
- **对比 ReAct**：ReAct 是「走一步看一步」，隐式逐步规划，灵活但短视、token 消耗大；Plan-and-Execute 是「先有总蓝图再落地」，全局性更强，方便插入审批、缓存和并行执行，但**错误计划会污染全局**。
- **选型判据**：任务路径强依赖外部环境反馈（网页导航、故障排查）→ ReAct；任务可分解、流程相对稳定、需要可审计的计划书（报告生成、批量数据处理、长链工作流）→ Plan-and-Execute。
- **🟡 追问：Re-planning 会不会「计划抖动」？** 会。缓解：限制重规划次数、局部重规划优先、在 state 中保留已验证事实、要求新计划必须说明与旧计划的差异（一致性检查）。

**Q：Reflexion 是什么？和「让模型自己检查一遍」有什么区别？**

- Reflexion 的核心是 **Action → Evaluation → Reflection → Retry**：执行后由 Evaluator 给反馈（分数/对错/缺失项），由 Reflector 生成**语言化的反思文本**（不是泛泛的"我要更仔细"，而是可执行的指导，如"应先确认单位换算"、"应先检索最新数据而非凭记忆"）。
- 反思文本作为**记忆**进入下一轮 prompt，形成可累积的「策略记忆」。
- **和自检的区别**：自检往往是一次性的、隐式的；Reflexion 把评估与反思**显式化、结构化、跨尝试复用**，工程上更易控制和评测。
- **适用范围**：可验证任务（代码能跑通、数学有标准答案）、易犯系统性错误的任务、预算允许多轮尝试的场景。
- **🟡 加分**：Re-planning 和 Reflexion 都"改正错误"，但前者调整的是**计划结构**（下一步怎么走），后者沉淀的是**策略经验**（下次怎么想）。

### 2.5 🔴 必考：工具调用（Function Calling）与 MCP

**Q：Function Calling 是怎么工作的？**

- **本质**：模型**不执行函数**，它只是根据你提供的工具描述（name / description / parameters JSON Schema）返回一个结构化的调用请求：`{"name": "get_weather", "arguments": {"city": "北京"}}`。
- **完整链路**：① 开发者注册工具定义 → ② 用户提问 → ③ 模型判断是否需要工具、返回 tool_call → ④ 应用层**校验参数** → ⑤ 调用真实服务 → ⑥ 把结果作为 `role: tool` 的消息回填给模型 → ⑦ 模型生成最终答案或继续调用。
- **🔴 安全边界**：模型只能「建议调用」，绝不能直接拥有数据库写权限或支付权限。**权限控制必须在应用层完成**，API Key 永远不要进上下文（模型只返回"调哪个工具、传什么参数"，Key 在执行层注入）。
- **🔴 工具调用幻觉的防治**（面试高频追问）：① 严格定义工具 Schema（名称、参数、类型、枚举值写清楚）；② 工具白名单（执行层只允许已注册工具，模型返回未注册工具名直接拦截）；③ 执行前参数校验（类型、取值范围），不符合就返回结构化错误让模型重新生成；④ 工具描述里写清"用途 + 输入输出 + 边界条件 + 示例"。
- **🔴 高频追问：工具返回结果过长怎么办？** 结果裁剪（只返回必要字段）、结构化压缩（表格转摘要）、二次摘要（用小模型压缩）、分页（让 Agent 按需取下一段）。
- **🔴 高频追问：一次调用多个工具，怎么控制顺序和依赖？** 无依赖的并行调用（parallel tool calls）；有依赖的串行（后一个的参数来自前一个的返回值）；在 Prompt 或图编排里显式声明依赖关系。

**Q：MCP 是什么？它和 Function Calling 什么关系？**

- **MCP（Model Context Protocol）** 是 Anthropic 提出的**工具/上下文接入的标准化协议**，类比「AI 领域的 USB-C」。
- **它解决的问题**：没有 MCP 时，每接一个新工具就要写一套私有适配代码，换个模型/框架还得重写。有了 MCP，工具开发者只需实现一次协议（提供 resources / tools / prompts 三类能力），所有支持 MCP 的宿主和模型都能复用。
- **和 Function Calling 的关系**：Function Calling 是**模型侧的能力**（模型会不会输出结构化调用请求）；MCP 是**工程侧的协议**（工具怎么被标准化地暴露和发现）。两者是不同层面的东西，MCP 服务器提供的工具最终仍通过 Function Calling 被模型调用。MCP 解决的是**可移植性和复用性**，不是模型能力。
- **🟡 加分（MCP vs A2A）**：MCP 偏「模型/应用如何安全访问外部工具和资源」，关注**人机边界**；**A2A（Agent-to-Agent）** 偏「多个 Agent 之间如何通信、委派、共享任务状态」，关注**智能体之间的协作边界**。MCP 解决"我怎么调用工具"，A2A 解决"我怎么把任务交给另一个 Agent 并拿回结果"。二者不是替代，是分层。
- **🟡 加分（MCP vs Skill）**：**MCP 是工具层的标准化，Skill 是能力层的复用**。Skill 把某个能力封装成「技能包」——定义能做什么、需要什么输入、输出什么格式、依赖哪些 MCP 工具。不同 Agent 之间可共享 Skill，新 Agent 组合现有 Skill 即可。两者配合才能让 Agent 系统规模化。

参考：[字节跳动 Agent 开发四面面经（21 题）](https://programmercarl.com/)、[MCP 协议详解（GitHub）](https://github.com/bcefghj/learn-nanobot/blob/main/docs/05-mcp-protocol/README.md)

### 2.6 🔴 必考：Agent 循环终止条件与错误恢复

**Q：Agent 执行中工具报错了怎么办？**

- **错误三分类（高分回答框架）**：
  1. **可重试错误**：网络超时、429 限流、临时依赖故障 → 指数退避重试（exponential backoff + jitter），设最大重试次数。
  2. **可修复错误**：参数缺失、格式不合法、类型错误 → **把错误摘要反馈给模型**，让它重新构造参数。
  3. **不可恢复错误**：权限拒绝、业务规则禁止、资源不存在 → 立即终止当前工具链，向用户解释，必要时转人工。
- **🔴 关键点**：**不要把原始堆栈/异常信息直接喂回模型** —— 要把错误提炼成结构化信息：`{error_code, retryable: bool, needs_human: bool, hint: "..."}`。
- **降级策略**：某个工具挂了，用备用方案顶上（搜索 Agent 挂了用本地知识库；主模型超时切小模型兜底）。
- **结果校验**：子 Agent / 工具的输出不能直接信任，要校验格式和内容（代码能不能编译、SQL 能不能执行、返回的商品 ID 在库里存在吗）。

**Q：怎么防止 Agent 无限循环？**

- 多层保险，不是单点措施：
  1. `max_iterations` 硬上限（最基础）。
  2. **重复检测**：记录最近几步的 `(工具名, 参数哈希)`，重复调用去重并告警。
  3. **进度判断**：要求模型每轮显式回答「我是否获得了足够信息」，无新增信息就升级跳出。
  4. **Observation 摘要**：工具结果先摘要再入上下文，避免上下文越滚越乱导致模型迷失。
  5. **失败工具冷却/禁用**：连续失败 N 次的工具进入冷却，防止反复撞墙。
  6. **Critic / Controller 节点**：独立的判断器监控轨迹是否仍在朝目标前进。
- **🔴 高分句**：「循环是控制问题，不只是提示词问题」—— 讲出这句会显著显得成熟。

### 2.7 🔴 必考：Agent 评测怎么做

**Q：Agent 效果怎么衡量？没有标注数据怎么办？**

- **🔴 第一性区分**：**LLM 评测测的是「模型能不能答对」，Agent 评测测的是「系统能不能做成」。**
- **三个根本差异**：① 多轮 vs 单轮（一个 task 可能 10–50 轮交互）；② 有状态 vs 无状态（会影响环境状态，必须验证结果）；③ **非确定性放大**（LLM 的随机性在多步交互中被放大，每步小偏差累积成大差异）。
- **🔴 最容易被忽视的坑：Transcript vs Outcome**
  - Transcript = Agent 在对话里说了什么（"已为您预订成功"）。
  - Outcome = 环境里实际发生了什么（数据库 Orders 表是不是真的有一行）。
  - **Agent 说的 ≠ 实际做的。** 至少 50% 的检查项必须验证 Outcome（DB 状态、API 调用记录、文件变更），不能全靠 Transcript。
- **三种 Grader 组合原则（必背）**：
  | 类型 | 确定性 | 成本 | 最适合 |
  |---|---|---|---|
  | Code-based（正则 / 单测 / DB 状态检查） | 完全确定 | 极低（毫秒） | **守门员**：拦住明显错误、验证硬事实 |
  | Model-based（LLM-as-Judge） | 非确定 | 中（每次调 LLM） | **艺术评委**：语气、个性化、完整性等主观维度 |
  | Human | 非确定 | 极高 | **黄金标准**：校准其他评分器、关键决策 |
  一句话：**能走确定性的走确定性。三者不是替换关系，是层层递进关系。**
- **LLM Judge 三大最佳实践（🟡 加分）**：① **Uncertain Escape Hatch** —— prompt 必须给 LLM 一个「不确定」出口（如 `INSUFFICIENT_INFO`），强制它不确定就说不确定，否则等于默认允许乱打分；② **Evidence Quote** —— 要求 judge 引用原文证据，防止编造评分理由；③ **One Dimension Per Call** —— 每次只评一个维度（准确性、语气、完整性分开调），一次性评所有维度会互相干扰。
- **pass@k vs pass^k（🟡 高频概念题）**：
  - `pass@k` = k 次尝试中**至少 1 次**成功的概率（"shots on goal"）→ 适合 coding agent，给多次机会衡量最佳情况。
  - `pass^k` = k 次尝试**全部**成功的概率 → 适合面向用户的 Agent。k=3、单次成功率 75% 时，只有约 42% 用户连续 3 次都满意。
- **Capability Eval vs Regression Eval（🟡）**：
  - Capability（能力）：期望 pass rate **30–50%**（有难度、有区分度），用于能力爬坡和模型选型。
  - Regression（回归）：期望 pass rate **≈100%**（历史通过的必须继续通过），用于防回退。
- **Agent 评测五大挑战（🟡 加分）**：① 非确定性（同 task 跑多次、报均值和置信区间，至少 10 次 trial）；② 错误传播/蝴蝶效应（一个 trial 内第 3 轮的偏差在第 10 轮放大成灾难）；③ 环境漂移（benchmark 环境冻结但真实环境在变，API/网页/数据都会过期）；④ Reward Hacking（UC Berkeley 发现 8 大 Agent benchmark 都能被 hack 到接近 100%）；⑤ **Transcript 欺骗**（最易忽略）。
- **🟡 极致加分句**：「做 Agent 评测的人必须**亲自读 transcript**。只靠分数你只知道过了没有，不知道原因。每个 eval run 至少读最高分、最低分、随机抽各 5 条。」
- **主流 Benchmark 名词**：SWE-bench Verified（软件工程 issue 修复）、WebArena（真实网页多步任务）、GAIA（通用助手多步推理）、AgentBench（8 类环境泛化）、**τ²-Bench**（航空/零售真实业务，工具+状态+政策，最接近「Agent 帮用户办事」）、**Tau-bench**（客服多轮）、**LoCoMo**（长对话长期记忆）。

参考：[Agent 评测 / Benchmark 彻底备战手册（AgentGuide）](https://github.com/adongwanai/AgentGuide/blob/main/docs/04-interview/18-agent-interview-playbooks/agent-evaluation-playbook.md)、[AI Agent 面试题库 · 编程实战篇](https://github.com/adongwanai/AgentGuide/blob/main/docs/04-interview/04-coding-questions.md)

### 2.8 🔴 必考：上下文漂移 / 长任务不偏离目标

**Q：长任务或复杂任务中，怎么保证模型不偏离原始目标？**

- 这个问题工程上叫**上下文漂移（context drift）**，也是字节、蚂蚁 Agent 岗的高频追问。
- 五个手段：
  1. **每轮注入原始目标**：在每轮 System Prompt / 用户消息里重复原始需求，相当于不断"提醒"。
  2. **阶段性自查**：要求 Agent 每执行几步就总结当前进度和剩余任务，用总结替代完整历史，既控 token 又保方向。
  3. **外部监督 Agent**：用独立的检查 Agent（质检员）监控主 Agent 的执行轨迹，发现偏了就拉回来。
  4. **任务分解 + 契约化**：长任务拆成短任务，每个短任务有明确的输入输出定义，完成后和预期对比，偏差大就及时修正。
  5. **上下文压缩**：摘要替代原始对话，释放窗口空间。
- **🟡 加分**：给每条注入的信息打「优先级标签」（goal / constraint / preference / history），压缩时按优先级裁剪。

参考：[字节跳动 Agent 开发四面面经](https://programmercarl.com/)

## 第 3 节 · RAG

> 面试出现率：**95%+**，且通常从「你们项目的 RAG 怎么做的」切入，然后连续追问到指标体系
> 高频公司：全行业（含半导体/制造业知识库场景）

### 3.1 🔴 必考：文档切分（Chunking）策略

**Q：chunk 大小和 overlap 怎么定？**

- **矛盾**：chunk 太小 → 语义上下文不完整，模型断章取义；chunk 太大 → 无关信息稀释注意力、检索精度下降、token 成本上升。
- **经验值**：512–1024 token，overlap 50–100 token（约为 chunk 的 10–15%）。overlap 的作用是避免关键信息恰好跨块被切断，但重叠太多会造成冗余召回和成本浪费。
- **🔴 高分点**：**先按文档结构切，再做长度约束，而不是只按固定字符数硬切。** FAQ 可用小块；合同、技术文档、工艺规范按标题/章节/段落/表格/代码块切。
- **进阶策略**：
  - **父子块（Parent-Child / Small-to-Big）**：用小块做检索（精度高），返回时替换成大块或整段（上下文完整）。
  - **语义切分（Semantic Chunking）**：计算相邻句子的 embedding 相似度，在相似度骤降处切分，保证语义边界。
  - **多粒度索引**：同时索引句子级、段落级、章节级摘要，按 query 类型路由。
- **🔴 半导体/制造场景的特殊性**（结合第 7 节）：文档里有大量表格（配方 Recipe、量测数据、参数规格）、SOP 步骤、图纸、专业缩写。需要 **Layout-aware 解析**（识别标题/正文/表格/页眉页脚）+ 表格转结构化（Markdown / JSON）+ 保留 metadata（工序号、机台号、版本号、生效日期）。

### 3.2 🔴 必考：Embedding 模型选择与相似度度量

**Q：embedding 是什么？怎么选模型？**

- embedding 把文本/图片/代码映射为固定长度稠密向量，把「语义相似」转化为「向量距离接近」。
- **选型维度**：语言（中文优先 BGE / GTE / Qwen-Embedding / M3E / Conan）、最大长度（512 还是 8K）、维度（768 / 1024 / 1536 / 2048）、是否支持指令前缀（instruction embedding）、是否支持稀疏+稠密混合输出（如 BGE-M3）、是否可本地部署。
- **🟡 加分（中等规模团队实践）**：不要迷信榜单，**在业务自己的评测集上跑 Recall@k 和 MRR 才是唯一标准**。换 embedding 是收益最大的单项优化之一（面经里常见 "Recall@5 从 65% → 82%"）。
- **相似度度量**：
  - **余弦相似度（Cosine）**：只看夹角，弱化模长，文本 embedding 最常用。
  - **点积（Dot Product）**：同时受方向和模长影响。**如果向量已归一化，点积排序与余弦等价**。很多向量库为了性能用内积。
  - **欧氏距离（L2）**：几何距离，高维下区分度下降。
  - **🔴 关键**：**选择和 embedding 模型训练时一致的度量方式**，否则召回会明显掉。
- **🔴 高频追问：embedding 模型升级怎么做？**
  - 最大风险：**新 query 向量和旧文档向量不在同一语义空间，混用会导致召回崩坏**。
  - 正确做法：**versioned index** —— 新老索引并行，摄取链路双写，新文档用新模型，老文档后台回填；线上用同一评测集灰度对比 Recall@k 和业务指标；稳定后下线旧索引。
  - **🔴 高分句：「绝对不要原地覆盖旧向量」**。

### 3.3 🔴 必考：向量数据库与 HNSW / IVF 索引原理

**Q：Milvus / FAISS / pgvector 怎么选？**

| 方案 | 定位 | 适合 |
|---|---|---|
| **FAISS** | 高性能相似度搜索**库**（不是数据库） | 本地实验、自建检索服务、要求底层可控 |
| **Milvus** | 分布式**向量数据库**，支持多索引类型、标量过滤、水平扩展 | 亿级以上规模、需要高可用和分布式 |
| **pgvector** | PostgreSQL **扩展** | 数据本来就在 PG、需要结构化过滤 + 向量检索同一套系统、规模千万级以内 |
| **Elasticsearch / OpenSearch** | 已有 ES 生态，支持 kNN | 已有全文检索体系，加向量召回最省事 |
| **Qdrant / Weaviate / Pinecone** | 专用向量数据库（含托管） | 快速上线、少运维、云原生 |

- **选型判据**：数据规模、过滤需求（metadata filtering）、团队运维能力、SLA、预算、是否需要事务一致性。

**Q：HNSW 和 IVF 的原理与取舍？**

- **HNSW（Hierarchical Navigable Small World，分层可导航小世界图）**
  - 结构：多层图。高层节点少、连接稀疏，负责快速导航到大致区域；低层节点多、连接更密，负责局部精细搜索。
  - 查询：从顶层入口点开始贪心搜索，逐层下降，最终在底层找到近邻。
  - 核心参数：`M`（每个节点的邻居数，越大越准越占内存）、`efConstruction`（建索引时的候选队列长度）、`efSearch`（查询时的候选队列长度，越大越准越慢）。
  - **优点**：召回率高、查询快（毫秒级）、工业成熟。**缺点**：**内存占用大**（图结构要常驻内存）、建索引慢、不支持高效增量删除。
- **IVF（Inverted File Index，倒排文件索引）**
  - 结构：先用 k-means 把向量空间聚成 `nlist` 个簇（Voronoi 单元），每个簇一个倒排列表。查询时只在最近的 `nprobe` 个簇里做暴力搜索。
  - 核心参数：`nlist`（簇数，经验 `√N`）、`nprobe`（查询时探测的簇数，越大越准越慢）。
  - **优点**：内存占用小（可配合 PQ 量化进一步压缩）、建索引快、适合超大规模。**缺点**：需要训练、对训练数据分布敏感、边界处的近邻容易漏。
- **🔴 一句话取舍**：**HNSW 换内存买速度和召回；IVF 换精度买内存和规模。** 亿级数据常用 `IVF_PQ`（倒排 + 乘积量化）压到内存能装下的量级；千万级以内用 HNSW 体验最好。
- **🟡 其他指数**：`IVF_FLAT`、`IVF_SQ8`（标量量化）、`IVF_PQ`、`DiskANN`（磁盘图索引，超大规模低成本）、`ScaNN`（Google，各向异性量化）、`Annoy`（树结构，只读场景）。
- **🟡 补充概念**：
  - **ANN（Approximate Nearest Neighbor，近似最近邻）**：牺牲少量精度换数量级速度提升，是向量检索的核心 trade-off。
  - **维度灾难（Curse of Dimensionality）**：维度升高后样本变稀疏、距离差异缩小，"最近邻"和"远邻"难以区分，导致暴力搜索和索引都变难。

参考：[做 RAG 不懂向量数据库，就像做后端不懂 MySQL（腾讯云社区）](https://cloud.tencent.cn/developer/article/2696436)、[LLM 算法岗面试常问八股汇总](https://www.cnblogs.com/moonout/p/19702578)

### 3.4 🔴 必考：混合检索（BM25 + 向量）与 RRF

**Q：为什么需要混合检索？怎么融合？**

- **稀疏检索（Sparse，代表 BM25）**：基于词频和逆文档频率的关键词精确匹配。擅长**法律条款号、产品型号、错误码、专有名词、缩写**；对同义改写不敏感。
  - BM25 公式直觉：`score(q,d) = Σ IDF(q_i) · (tf·(k1+1)) / (tf + k1·(1 - b + b·|d|/avgdl))`。`k1` 控制词频饱和，`b` 控制文档长度归一化。
- **稠密检索（Dense）**：基于 embedding 的语义相似匹配，对同义表达和跨语言更稳，但对精确串匹配弱。
- **混合检索（Hybrid）**：两条通道并行召回，再融合。真实查询既有"我要找这个词"的成分，也有"我要表达这个意思"的成分，所以工业界最终大多走向 hybrid。
- **融合方法**：
  - **RRF（Reciprocal Rank Fusion，倒数排名融合）**：`score(d) = Σ_i 1 / (k + rank_i(d))`，`k` 通常取 60。**只用排名不用分数**，天然规避了两路分数不可比的问题，是面试标准答案。
  - **加权求和**：需要归一化两路分数，权重需要调，跨 query 不稳定。
  - **学习排序（Learning to Rank）**：用标注数据训一个融合模型，效果最好但成本最高。
- **🟡 加分**：融合后**必须接 rerank** —— 混合检索解决"召回全不全"，rerank 解决"排序准不准"。

### 3.5 🔴 必考：Rerank（重排序）

**Q：什么是 reranker？什么时候用？**

- **位置**：初步召回之后、拼进 prompt 之前。**两阶段检索架构**：粗排（召回）→ 精排（rerank）。
- **原理差异**：
  - 召回用的 **Bi-Encoder（双塔）**：query 和 document 分别独立编码成向量，可以离线预计算文档向量、用 ANN 快速检索。**快，但精度低**（query 和 doc 没有交互）。
  - rerank 用的 **Cross-Encoder（交叉编码器）**：把 `[query, document]` 拼在一起送进模型，让两者做 full attention 交互，输出一个相关性分数。**准，但没法预计算**，必须对每个候选现算，所以只能用在少量候选上。
- **工程实践**：`top-50 ~ top-100` 粗召回 → rerank → 只把 `top-3 ~ top-5` 高质量 chunk 传给 LLM。**不要对全库做 rerank**，成本和延迟会失控。
- **常见 rerank 模型**：BGE-Reranker 系列、Cohere Rerank、Jina Reranker、Cross-Encoder/ms-marco。
- **🟡 追问：加了 rerank 延迟涨了怎么办？** 缩小候选集、用更小的 rerank 模型、对 rerank 结果做缓存、异步预取、只在低置信 query 上触发。

### 3.6 🔴 必考：查询改写（Query Rewriting）与 HyDE

**Q：用户问得很口语/很短，检索效果差怎么办？**

- **Query Rewriting（查询改写）**：用 LLM 把口语化问题改写成检索友好的形式（补全主语、展开缩写、生成多个查询变体）。
- **Query Expansion / Multi-Query**：生成 3–5 个不同角度的查询并行检索，再融合结果，提升覆盖率。
- **HyDE（Hypothetical Document Embeddings，假设性文档嵌入）**：
  - 思路：用户问题太短太口语，直接做 embedding 不稳定。先让 LLM **"假想"出一段可能回答该问题的文档**，对这段假想文档做 embedding，再用它去检索真实语料。
  - 原理：**假想文档和真实文档在语义空间上更接近**（都是"答案形态"的文本），比"问题形态"的 query 更匹配。
  - 缺点：如果假想文档偏题，会把检索带歪。适合作为增强策略，不适合作为默认唯一方案。
- **RAG-Fusion**：多通道检索（embedding + keyword + 多 query 变体）+ 融合（RRF / voting / 再生成），更全更稳，但成本高、延迟大、工程复杂。
- **🟡 追问：查询改写会不会引入幻觉？** 会。所以要保留原始 query 作为一路检索通道，并对改写结果做一致性检查（改写后的意图要和原问题一致）。

### 3.7 🔴 必考：RAG 评估指标（Recall@k / MRR / NDCG / RAGAS）

**Q：RAG 系统怎么评估？用什么指标？**

- **🔴 分两层：检索侧评估 + 生成侧评估。** 只回答"看召回率和人工抽查"是减分项，面试官会立刻追问"召回率具体怎么算"。

**检索侧（能不能找到）：**
| 指标 | 公式 | 含义 | 工程意义 |
|---|---|---|---|
| **Recall@K** | 检索到的相关 chunk 数 / 全部相关 chunk 数 | 相关内容有没有被找到 | **<70% 说明检索侧有严重问题，后面加 rerank 也救不回来** |
| **Precision@K** | 检索到的相关 chunk 数 / K | 找到的内容有多少是相关的 | 低说明噪声太多，会稀释模型注意力 |
| **MRR** | `(1/N) Σ (1 / rank_i)` | 第一个相关结果的排名倒数均值 | 最好的有没有排前面（用户只看前几条） |
| **NDCG@K** | `DCG@K / IDCG@K`，`DCG@K = Σ rel_i / log2(i+1)` | 考虑排序位置 + 相关度分级 | 综合排序质量，用于精确对比两个方案 |
| **HitRate@k** | top-k 中至少命中 1 个的比例 | 最基础的命中率 | 快速监控 |

- **Recall/Precision 的平衡实践**：**用大 K 保 Recall，用 Rerank 保 Precision** —— 先取 top-20~50 保证召回，再 rerank 把精度拉回来，最终只传 3–5 条给 LLM。
- **NDCG 举例**：相关性分级 0–3 分，位置越靠后折扣越重；`IDCG` 是理想排序的 DCG，两者相除归一化到 0–1。

**生成侧（用得好不好）—— RAGAS 框架四维度（必背）：**
| 指标 | 定义 | 评估方法 | 工程意义 |
|---|---|---|---|
| **Faithfulness（忠实度）** | 答案是否忠实于检索到的上下文，有没有编造 | 把答案拆成多个陈述，用 LLM 判断每个陈述能否从上下文推导；`= 可推导陈述数 / 总陈述数` | 衡量 RAG 是否真正 Grounded，**这是 RAG 相比纯 LLM 的核心优势** |
| **Answer Relevancy（答案相关性）** | 答案是否真正回答了问题，有没有答非所问 | 用 LLM 根据答案**反向生成 N 个可能的问题**，算这些问题与原问题的语义相似度均值 | 防止"相关但不精准" |
| **Context Relevancy（上下文相关性）** | 检索到的上下文里有多少内容对回答有用 | LLM 从每个 chunk 中提取相关句子；`= 相关句子数 / 总句子数` | 反向评估 chunking 和检索质量 |
| **Context Recall（上下文召回）** | 标准答案的关键信息有多少出现在检索到的上下文中 | 需要 ground truth，LLM 判断标准答案的每个陈述能否从上下文推导 | 从生成角度评估检索完整性 |

- **四者关系（🔴 面试可背）**：`Context Recall + Context Relevancy` = 检索质量；`Faithfulness + Answer Relevancy` = 生成质量。
  - **Context Recall 低 → 后面指标再高也没用**，因为关键信息根本没检索到。
  - **Context Relevancy 低 → 会拉低 Faithfulness 和 Answer Relevancy**，噪声太多干扰生成。
- **Faithfulness 算例**：上下文说"年假 10 天，满 3 年增至 15 天"；答案说"年假 10 天，满 3 年 15 天，满 5 年 20 天"。前两句可推导，第三句编造 → `Faithfulness = 2/3 = 66.7%`。
- **🔴 评估集怎么建（三种方法）**：① 人工构造（质量最高、成本最高，50–200 条即可建 baseline）；② 真实日志采样（质量中等，适合持续监控）；③ LLM 生成（成本最低，但问题过于理想化，不代表真实用户行为）。**建议：先用方法 ③ 搭框架，再用方法 ① 建核心场景高质量集。**
- **🔴 优化闭环（必背五步）**：建立 baseline → 定位瓶颈 → 单变量优化 → 对比验证 → 持续迭代。
  - `Recall@5 < 70%` → 优先优化检索召回（换 embedding、改 chunk、加混合检索、扩大 K）
  - Recall 高但 Precision 低 → 加 Rerank
  - Context Relevancy 低 → 优化 Chunking 或减少 top-K
  - Faithfulness 低 → 改进 Prompt 约束 / 减噪声 / 换更强模型
  - Answer Relevancy 低 → 检查 Query 理解和模型能力
  - **每次只改一个变量**，否则无法归因。
- **🟡 加分（线上采用率）**：离线指标涨了线上反而掉，是常见坑。原因通常是 ① 测试集偏差（真实用户问法千奇百怪）；② 延迟变长（加 rerank 后 P95 从 2s 涨到 5s，用户等不及）；③ 答案变长/机器腔（为了 Faithfulness 把资料全塞进答案）。
  - **线上指标**：复制率、点赞率、点踩率、无追问率、停留时长、人工接管率。
  - **🔴 高分句：离线指标是方向盘，线上采用率是目的地。**
- **🟡 加分（评估成本控制）**：RAGAS 一条评估要几千 token，是原问答的 5–8 倍。省钱办法：采样评估（每天 1–5%）、分级评估（高风险查询实时评）、单项评估（根据当前优化目标只跑 1–2 个指标）、用便宜模型做 judge（成本降 10 倍，准确率只降约 5%）。

参考：[RAG 评估体系：检索召回率、精准率、MRR、NDCG 与生成质量 RAGAS 框架详解（代码随想录）](https://github.com/youngyangyang04/llm-master/blob/main/docs/llm/app/rag_evaluation.md)

### 3.8 🟡 加分：多跳问答（Multi-hop QA）与 GraphRAG

**Q：一个问题需要跨多个文档才能回答，怎么处理？**

- **问题本质**：单轮检索只能拿到"局部相关"的片段，但答案需要 A→B→C 的链式推理。
- **方案一：迭代检索（Iterative Retrieval / Self-Ask）**：把问题分解成子问题，逐个检索并回答，用前一步的答案构造下一步的查询。
- **方案二：查询分解（Query Decomposition）**：用 LLM 把复杂问题拆成子查询列表，并行/串行检索后汇总。
- **方案三：GraphRAG（知识图谱增强）**：把文档抽成实体-关系图，用图上的社区摘要回答"全局性"问题。适合"这份资料整体讲了什么"这类需要跨文档归纳的 query。代价是索引成本高。
- **方案四：Agentic RAG**：把 RAG 作为 Agent 的一个工具，让 Agent 自己决定"要不要检索、检索几次、换个 query 再检索"，天然支持多跳。
- **🟡 追问：多跳怎么评估？** 除了 Recall@k，还要看**链路的每一步是否正确**（中间答案准确率），以及**端到端的最终答案正确率**。只测最终结果无法定位是哪一跳断了。

## 第 4 节 · 多智能体与工程框架

> 面试出现率：**85%**（框架对比 + 状态机 + 记忆 + 成本优化）

### 4.1 🔴 必考：LangChain / LangGraph / LlamaIndex / AutoGen / CrewAI 的差异

**Q：这几个框架有什么区别？你项目用了哪个，为什么？**

- **LangChain**：最早的 LLM 应用「全家桶」，提供 Models / Prompts / Chains / Agents / Memory / Tools / Retrievers / Callbacks 等抽象。定位是**通用组件库 + 生态整合**。核心概念 `AgentExecutor` 驱动「模型决策 → 工具执行 → 结果回填 → 再决策」的循环，统一处理迭代限制和错误。**缺点**：抽象层多、版本迭代快、复杂流程的可控性差。
- **LangGraph**：LangChain 生态下的**图编排框架**，把 Agent 工作流画成**状态图**：Node 是处理步骤（调模型、调工具、审核），Edge 是流转关系。定位是**复杂流程的可控编排**。相比 AgentExecutor 的优势：显式支持**条件分支、循环回退、并行、人在环路（Human-in-the-loop）、检查点（Checkpoint）/ 持久化状态**。
- **LlamaIndex**：**数据/检索框架**，强项在**索引构建和检索策略**（多种 Index、Node Parser、Query Engine、Router、SubQuestion Query Engine）。定位是**以数据为中心的 RAG 引擎**。做深度检索优化比 LangChain 更顺手。
- **AutoGen（Microsoft）**：**多 Agent 对话框架**，核心是「多个可编程 Agent 通过对话协作」，支持 GroupChat、Manager 编排、代码执行器（Code Executor）。定位是**可编程的对话式多智能体**。
- **CrewAI**：**角色驱动的团队协作框架**，核心抽象是 Agent（角色 + 目标 + 背景故事 + 工具）+ Task + Crew + Process。定位是**流水线式的角色分工**，上手最快、心智负担最低。
- **🟡 选型建议（讲出这个显得有判断力）**：
  - 单 Agent + 工具循环、想快速起步 → LangChain / 各家原生 SDK
  - 复杂业务流、需要分支/回退/人工审核/断点续跑 → **LangGraph**
  - 检索是核心（多索引、多种 chunk 策略、复杂 query 路由）→ **LlamaIndex**
  - 多角色协作、需要 Agent 间自由对话 → **AutoGen**
  - 流程化的角色分工（调研→写作→审核）→ **CrewAI**
  - **🔴 高分点**：框架只是脚手架，「ReAct 循环 + 工具注册表 + 状态管理」的原理才是根本。能说出「我自研了一个轻量循环，因为 LangChain 的抽象让我无法精细控制重试和 token 预算」比只会报框架名强得多。

### 4.2 🔴 必考：LangGraph 的状态机 / 检查点 / 人在环路

**Q：LangGraph 的 StateGraph 怎么工作？检查点解决什么问题？**

- **State（状态）**：通常用 `TypedDict` 或 dataclass 定义 schema，所有节点共享。节点函数签名是 `state -> partial_state_update`（返回增量更新，不是全量覆盖）。
- **Reducer（归约器）**：多个节点写同一字段时，需要指定合并策略 —— `append`（追加，如消息列表）还是 `replace`（覆盖）。**这是面试高频追问点**：不加 reducer 会导致并发写入互相覆盖。
- **Node（节点）**：一个处理步骤（调 LLM、执行工具、人工审核、数据校验）。
- **Edge（边）**：
  - 普通边：`A → B`，执行完 A 走 B。
  - **条件边（Conditional Edge）**：根据 state 动态路由，例如 `if needs_human_review(state): goto "human"; elif tool_error(state): goto "repair"; else: goto "continue"`。
- **Checkpoint（检查点）**：每步执行后把完整 state 持久化（内存 / SQLite / Postgres / Redis）。解决三类问题：
  1. **容错**：进程崩溃后能从最近检查点恢复，不用从头重跑（长任务最关键）。
  2. **人在环路**：图执行到 `interrupt` 节点暂停，把 state 存下来，等人工审批后用同一个 `thread_id` 恢复执行。
  3. **时间旅行调试（Time Travel）**：回放某个历史状态、改一个字段后重跑，用于复现和调优。
- **人在环路（Human-in-the-Loop, HITL）的落地**：高风险操作（删数据、发邮件、下单、改配方）前必须 `interrupt`，把「我打算做什么」展示给人确认，确认后再继续。**这是 Agent 从 Demo 走向生产的必经之路。**
- **🟡 追问：图和普通脚本编排的区别？** 图把控制流**显式化**，分支/回环/人机节点是一等公民，可观测性和可维护性都更好；脚本编排在流程复杂后会变成难以维护的 if-else 面条。

参考：[LangGraph Orchestration](https://github.com/ombharatiya/ai-system-design-guide/blob/main/09-frameworks-and-tools/02-langgraph-orchestration.md)、[智能体面试准备：LangChain / LlamaIndex / CrewAI 深度对比（CSDN）](https://blog.csdn.net/thesky123456/article/details/163259891)

### 4.3 🔴 必考：Agent 记忆系统（短期 / 长期 / 情景）

**Q：Agent 的记忆怎么做？短期和长期记忆怎么压缩？**

- **🔴 分层记忆（面试标准框架）**：
  1. **工作记忆 / 短期记忆（Working / Short-term Memory）**：当前对话上下文、当前任务状态，放上下文窗口里，就是 Conversation Buffer。
  2. **会话摘要记忆（Session Summary）**：把长对话压缩成「用户诉求 + 已尝试动作 + 待确认事项」，替代原始历史，省 token 但保留关键信息。
  3. **长期记忆（Long-term Memory）**：持久化存储。向量库（语义检索）+ 结构化数据库（精确查询，如用户 ID、会员等级）+ KV（偏好开关）。
  4. **语义记忆（Semantic Memory）**：领域知识和事实，主要由 RAG 提供。
  5. **情景记忆（Episodic Memory）**：具体历史事件（"上次这个用户因为发票问题投诉过"），按时间线和情境检索。
- **短期压缩三手段**：
  - **滑动窗口**：只保留最近 N 轮，最简单也最粗暴（会丢关键约束）。
  - **对话摘要**：模型把早期对话总结成一段，token 省很多但关键信息可能被摘要丢掉。
  - **重要信息提取**：把关键决策、约束条件、用户偏好单独结构化存一份，**每轮都注入**，不被摘要冲掉。
- **长期记忆三要点**：
  - **写入策略**：不是所有对话都值得长期记忆。只有对未来服务真正有帮助且合规允许的信息才写入（写入要经过字段化和隐私审查）。
  - **检索与重排**：向量召回 + 时间衰减 + 相关性重排。
  - **更新与遗忘（🟡 高频追问）**：事实变更时怎么处理旧记忆？—— 版本化 + 软删除 + 时效标记；过期记忆定期清理；新旧冲突时以时间戳新的为准，或触发澄清。
- **🔴 高分答法（四层结构讲记忆）**：
  ```
  [最近 N 轮对话]        → 实时上下文（工作记忆）
  [会话摘要]             → 长会话压缩（情景记忆）
  [用户画像 / CRM / 偏好] → 持久业务记忆（结构化）
  [知识库 / 政策文档]     → 外部知识记忆（RAG）
  ```
- **🔴 追问：为什么不用上下文窗口直接存所有历史？** 一是成本（token 线性甚至平方增长），二是 Lost in the Middle 导致有效利用率下降，三是无法跨会话、无法按需检索、无法权限隔离。

参考：[字节跳动 Agent 开发四面面经（记忆系统）](https://programmercarl.com/)、[AI Agent 面试问题集（记忆类型）](https://github.com/kakaCat/langchain-learn/blob/main/AI_Agent_Interview_Questions.md)

### 4.4 🔴 必考：上下文工程（Context Engineering）

**Q：什么是上下文工程？和提示词工程什么关系？**

- **提示词工程（Prompt Engineering）**：优化"指令怎么写"，关注 System Prompt、Few-shot、CoT 的组织方式。
- **上下文工程（Context Engineering）**：更上层 —— 决定**每一步往上下文窗口里放什么、放多少、按什么顺序放**。包括：System Prompt、工具定义、检索结果、记忆、工具返回值、历史对话、当前任务状态。
- **🔴 核心矛盾**：需要放的东西越来越多（系统提示 + 历史 + 检索结果 + 工具返回），但窗口有限且**不是越满越好**（注意力稀释）。
- **工程手段**：
  - **压缩**：摘要、关键信息提取、Observation 摘要。
  - **选择**：RAG 按需检索而非全塞、工具结果裁剪字段、只注入相关记忆。
  - **排序**：重要信息放**开头和结尾**（规避 Lost in the Middle）。
  - **隔离**：不同来源的内容加显式标记（`<retrieved_doc>` / `<user_input>` / `<tool_result>`），既帮助模型区分，也是 Prompt Injection 的第一道防线。
  - **预算管理**：为每一类内容设 token 配额，超了就按优先级裁。
- **🟡 加分术语**：「Context Budget」（上下文预算）和「Context Rot」（上下文腐化）说出来会很加分。

### 4.5 🔴 必考：成本与延迟优化

**Q：怎么降低 Agent 的 token 消耗 / 响应延迟？**

- **降低 Token 成本**：
  1. **模型分级路由（混合路由）**：简单分类/格式转换用 7B 或 Haiku 级别小模型，复杂推理和核心决策用大模型。**简单任务走小模型省成本，复杂任务走大模型保质量。**
  2. **Prompt 压缩**：精简 System Prompt、工具描述（工具描述本身很占 token！）、减少 few-shot 示例数量。
  3. **上下文管理**：滑动窗口 + 摘要 + 检索按需。
  4. **缓存**：见下。
  5. **批处理**：合并请求，提高 GPU 利用率，降低单请求成本。
  6. **限制步数**：`max_iterations` 和 token 预算硬上限。
- **降低延迟**：
  1. **并行工具调用**：无依赖的工具同时调。
  2. **流式输出（Streaming / SSE）**：降低首字延迟（TTFT）的感知。
  3. **缓存**：精确缓存（相同输入直接返回）+ **语义缓存（Semantic Cache，命中语义相近的历史 query）**。语义缓存要注意**阈值调优** —— 阈值太松会返回错误答案，太严命中率低。
  4. **模型选择**：小模型 / 更快的推理框架（vLLM + 连续批处理）。
  5. **Prompt 优化**：减少不必要的推理步骤（比如让简单任务不走 Thought）。
  6. **预取（Prefetch）**：根据对话走向提前触发可能的检索。
- **🔴 权衡原则**：**简单子任务用小模型快速完成，核心决策用大模型保证质量。** 别一刀切。
- **🟡 追问（多 Agent 场景）**：多 Agent 并发调 API 很容易打爆速率限制（429）。需要**限流器**，通常用**令牌桶算法** —— 设定平均速率和突发上限，短时允许多发但总体受控；关键路径（主 Agent 规划）优先级高于非关键路径（子 Agent 搜索）。

### 4.6 🟡 加分：多智能体架构与通信

**Q：多 Agent 架构下主 Agent 和子 Agent 怎么通信？异常怎么处理？**

- **常见模式（三种，必背）**：
  1. **Manager-Worker（管理者-工作者）**：主 Agent 拆任务，多个子 Agent 执行，主 Agent 汇总。
  2. **Pipeline（流水线）**：研究 → 分析 → 写作 → 审核，串行接力。
  3. **Debate / Critic（辩论-评审）**：多个 Agent 给不同方案，裁判或评审 Agent 选择 / 打分。
- **通信链路设计**：
  - **消息队列模式**：主 Agent 把子任务放进队列，子 Agent 取任务执行，结果写回队列，主 Agent 收集后决定下一步。好处是**解耦**（子 Agent 之间不直接通信），逻辑清晰、易排查。
  - **共享状态（Shared State）**：所有 Agent 读写同一份图状态（LangGraph 风格），需要严格的 schema 和 reducer 防冲突。
  - **协议层**：A2A 标准化消息格式；AG-UI 标准化前端交互反馈。
- **异常处理四层**：① **超时机制**（子 Agent 执行太久就 kill，返回兜底结果，不能让整个系统卡死）；② **重试策略**（换方式重试或换子 Agent 做，设最大次数）；③ **降级方案**（某子 Agent 挂了用更简单的方式顶上）；④ **结果校验**（子 Agent 输出不能直接信任，要校验格式和内容）。
- **🔴 关键问答：多 Agent 一定比单 Agent 更强吗？**
  - **不一定。** 更多 Agent 带来**协调成本、错误级联、对话冗长、延迟和 token 成本暴涨**、调试困难。
  - 收益场景：任务可清晰分工、有独立评估机制、需要角色分离（生成者 + 审查者）或上下文隔离。
  - **🔴 高分句**：多 Agent 的优势不是"更智能"，而是**角色分离、上下文缩小、可控性增强**。如果任务边界清晰、协调成本大于收益，**单 Agent + 强工具**往往更简单高效。
- **🟡 追问：怎么避免多 Agent「互相附和」（sycophancy）？** ① 引入独立审查角色（用不同 prompt / 不同模型）；② 基于规则的检查（单测、lint）；③ 外部工具验证（检索、计算器）；④ 明确停止条件和异议处理流程；⑤ 让批评者先给结论再给理由，避免被生成者的论述带偏。

## 第 5 节 · 工程与部署

> 面试出现率：**80%**（开发岗几乎必问，算法岗问 KV Cache + 量化的更多）

### 5.1 🔴 必考：vLLM / PagedAttention / 连续批处理

**Q：PagedAttention 是什么？它降低了显存占用吗？**

- **🔴 精确回答（这是个易错题）**：PagedAttention **不降低 KV Cache 的绝对大小**，它降低的是**显存碎片（fragmentation）和浪费**，从而显著提升**并发吞吐**。
- **问题背景**：主流推理框架为每个请求预分配一块**连续**的 KV Cache 显存（按 max_seq_len 预留），但实际生成长度远小于上限，导致大量内部碎片和外部碎片，显存利用率可能只有 20–40%。
- **PagedAttention 的做法**：借鉴操作系统虚拟内存分页 —— 把 KV Cache 切成固定大小的 **block**（如 16 个 token），用 **block table** 做逻辑到物理的映射。block 不需要连续，可以按需分配、非连续存放。
- **收益**：显存浪费降到 4% 以下，同样显存能跑更多并发请求；配合 **Copy-on-Write** 还支持**前缀共享**（多个请求共享同一个 system prompt 的 KV block）。
- **配套技术**：
  - **Continuous Batching（连续批处理 / 迭代级调度）**：传统静态 batch 要等 batch 里最长的请求生成完才能释放 GPU；连续批处理在每个 decode step 后检查，完成的请求立刻退出、新请求立刻插入，GPU 利用率大幅提升。
  - **Chunked Prefill**：把长 prompt 的 prefill 切成小块，与 decode 请求混批，避免长 prefill 阻塞短请求的延迟。
  - **Prefix Caching**：相同前缀（system prompt、few-shot 示例）的 KV 复用，对 Agent 场景（大量共享 system prompt）收益很大。
- **🟡 补充**：**Prefill 阶段是 compute-bound**（计算密集，处理整个输入 prompt，算 TTFT）；**Decode 阶段是 memory-bound**（带宽密集，逐 token 生成，算 TPOT）。这两个阶段的瓶颈完全不同，优化手段也不同。

参考：[27届大模型面试准备：连续批处理与 PagedAttention（CSDN）](https://blog.csdn.net/thesky123456/article/details/165599424)

### 5.2 🔴 必考：量化（GPTQ / AWQ / INT8 / FP8）

**Q：GPTQ 和 AWQ 有什么区别？什么场景用哪个？**

- **量化目标**：把权重从 FP16（16 bit）压到 INT8 / INT4，减少显存占用和内存带宽需求（decode 阶段是带宽瓶颈，所以量化对速度提升明显）。
- **GPTQ（GPT Quantization）**：
  - 属于**训练后量化（PTQ, Post-Training Quantization）**。
  - 思想源自 OBQ（Optimal Brain Quantization）：**逐层、逐列**量化，用 **Hessian 矩阵的逆**来估计每个权重的重要性，量化一个权重后用剩余未量化的权重**补偿量化误差**（把误差分摊到后续列）。
  - 特点：量化过程较慢（需要校准数据跑 Hessian），4 bit 下精度略好，硬件友好性一般。
- **AWQ（Activation-aware Weight Quantization）**：
  - 核心观察：**不是所有权重同等重要** —— 那些对应**激活值大的通道（salient channels）**更重要，量化时应该被保护。
  - 做法：对重要通道乘一个 scale 因子放大后再量化，推理时再缩回来（等价变换）。这样重要通道的相对量化误差更小。
  - 特点：量化过程快、不需要反向传播、对硬件更友好、4 bit 下精度接近甚至优于 GPTQ。
- **精度档位经验（工程判断）**：
  - **INT8 / FP8**：显存省约一半，精度损失很小（<1%），是**最稳妥的线上选择**。
  - **INT4（GPTQ/AWQ）**：显存省到 1/4，适合单卡部署大模型或预算敏感场景，但**某些任务（特别是数学推理、长链逻辑）掉点明显，不能无脑量化**。
  - **GGUF**：llama.cpp 生态的格式，支持 CPU/Metal 混合推理和多种量化等级（Q4_K_M 等），适合**本地/边缘部署**，不适合高并发服务。
  - **🔴 一句话选型**：稳定性优先 → INT8/FP8；单卡装大模型 → INT4 + AWQ；本地跑 → GGUF。
- **🟡 追问：量化的误差账怎么算？** 权重量化误差会被激活值放大：`输出误差 ≈ Σ (ΔW_i × X_i)`。激活值大的通道（`X_i` 大）即使 `ΔW_i` 相同，对输出贡献的误差也更大 —— 这正是 AWQ 的核心洞察。

参考：[27届大模型岗面试准备：模型量化实战（CSDN）](https://blog.csdn.net/thesky123456/article/details/163290779)

### 5.3 🔴 必考：吞吐与延迟指标（TTFT / TPOT）

**Q：怎么衡量推理服务的性能？**

- **TTFT（Time To First Token，首字延迟）**：从请求发出到收到第一个 token 的时间，主要由 **prefill** 阶段决定，受输入长度影响大。**流式体验的关键指标**。
- **TPOT / ITL（Time Per Output Token / Inter-Token Latency，每 token 延迟）**：生成阶段相邻 token 的平均间隔，由 **decode** 阶段决定，受模型大小、量化、batch 大小影响。
- **端到端延迟（E2E Latency）** ≈ `TTFT + TPOT × 输出 token 数`。
- **吞吐（Throughput）**：单位时间处理的 token 数或请求数（tokens/s、req/s）。
- **Goodput**：**满足 SLA 的有效吞吐** —— 比如"TTFT < 1s 且 TPOT < 50ms 的请求数/秒"。只看裸吞吐会掩盖大量超时请求。
- **🔴 核心权衡**：**batch 越大 → 吞吐越高，但单请求延迟越高**（要和别人抢 GPU）。所以是可恶的三角：吞吐、延迟、成本。
- **🟡 优化手段对应表**：
  | 目标 | 手段 |
  |---|---|
  | 降 TTFT | 缩短 prompt、Prefix Caching、Chunked Prefill、更快的 prefill 硬件 |
  | 降 TPOT | 量化、投机解码、GQA、更小模型 |
  | 提吞吐 | 连续批处理、PagedAttention、增大 batch、张量并行 |
- **🟡 投机解码（Speculative Decoding）**：用一个小 draft 模型快速生成 k 个候选 token，大模型**一次前向**验证这 k 个。**关键性质：无损** —— 通过 rejection sampling 策略，输出分布与直接用大模型生成**完全一致**。加速比取决于接受率（acceptance rate），典型 2–3×。

### 5.4 🔴 必考：显存估算（面试常要求现场算）

**Q：部署一个 7B 模型需要多少显存？**

- **权重显存 = 参数量 × 每参数字节数**
  - 7B FP16 = 7 × 2 = **14 GB**
  - 7B INT8 = **7 GB**；7B INT4 ≈ **3.5 GB**
  - 70B FP16 = **140 GB**（需要多卡）
  - DeepSeek-V3（671B 总参 / 37B 激活）FP8 ≈ **671 GB** —— MoE 省的是**算力**不是**显存**（所有专家都要装进显存）。
- **KV Cache 显存** = `2 × L × n_kv_heads × d_head × seq_len × batch × bytes`
  - **算例**：Qwen2.5-7B（L=28, n_kv_heads=4, d_head=128）FP16，seq=8192，batch=1：
    每 token 每层 = `2 × 4 × 128 × 2 B = 2048 B = 2 KB`
    全模型每 token = `2 KB × 28 = 56 KB`
    8192 token ≈ `56 KB × 8192 ≈ 0.45 GB`
    batch=32 ≈ **14.4 GB** ← 超过权重本身！
- **其他开销（常被忽略，要主动提）**：激活值（activation）、CUDA context / 框架开销（约 1–2 GB）、通信 buffer（并行时）、碎片。
- **经验公式（线上部署快速估算）**：
  ```
  所需显存 ≈ 权重显存 × 1.2 + KV Cache（按目标并发和上下文算）+ 2 GB 框架开销
  ```
- **🔴 面试答题模板**：「先看权重，7B FP16 是 14 GB；再看 KV Cache，按我们的并发 32、上下文 8K 算是 14 GB；加上框架开销 2 GB，总共约 30 GB，所以单张 24G 卡不够，需要 40G 或 A100，或者上 AWQ INT4 把权重压到 4 GB、KV 用 FP8 压到 7 GB，总共约 13 GB 就能单卡跑。」

### 5.5 🔴 必考：Python 工程 / FastAPI / 异步 / 流式输出

**Q：FastAPI 里怎么处理 LLM 的流式输出？异步有什么坑？**

- **流式输出用 SSE（Server-Sent Events）**：`StreamingResponse` + `async generator`，媒体类型 `text/event-stream`。每个 chunk 用 `data: {...}\n\n` 格式推送。也可以用 WebSocket（双向，适合需要中途打断的场景）。
- **异步要点**：
  - `async def` 里**绝不能调用阻塞的同步 I/O**（`requests`、`time.sleep`、同步 DB 驱动）—— 会阻塞整个事件循环，所有并发请求一起卡住。要用 `httpx.AsyncClient`、`asyncio.sleep`、`asyncpg`，或者用 `run_in_executor` / `anyio.to_thread` 把阻塞调用丢到线程池。
  - **GIL**：CPython 的 GIL 让同一进程同一时刻只有一个线程执行 Python 字节码。所以 CPU 密集型任务用**多进程**（`ProcessPoolExecutor`）而不是多线程；I/O 密集型任务用**异步协程**最合适（LLM API 调用就属于这类）。
  - **连接池**：`AsyncClient` 要复用（全局单例），每次请求新建客户端会耗尽端口和 TLS 握手开销。
  - **超时与取消**：LLM 调用必须设 `timeout`；客户端断开时要取消上游请求（`asyncio.CancelledError` 处理），否则 token 白烧。
  - **背压（Backpressure）**：生产端比消费端快时要限流，否则内存爆掉。用 `asyncio.Queue(maxsize=N)` 做有界队列。
- **工程规范**：配置用 `pydantic-settings` 从环境变量读（API Key 绝不硬编码）；接口用 Pydantic 模型做输入校验；用 `lifespan` 管理模型/客户端的启动和释放；结构化日志（JSON）。

### 5.6 🔴 必考：可观测性（LangSmith / Langfuse）

**Q：Agent 上线后出问题怎么定位？**

- **核心概念：Trace / Span**（借鉴 OpenTelemetry）：
  - **Trace** = 一次完整请求的全链路（用户提问 → 规划 → 检索 → 工具调用 → 生成 → 返回）。
  - **Span** = trace 里的一个步骤，记录输入、输出、耗时、token 数、模型名、工具名、错误。
- **工具选型**：**LangSmith**（LangChain 官方，Trace / Debug / Monitor / Evaluate 一体，与 LangChain 生态无缝）、**Langfuse**（开源可自托管，适合数据不能出内网的场景）、**Phoenix（Arize）**、**OpenTelemetry + Grafana**（通用可观测栈）。**🟡 2026 春招热门技术点。**
- **怎么定位"Agent 慢在哪"**：
  1. 看 trace 的 **span 瀑布图**，找出耗时最长的 span。
  2. 常见瓶颈：**串行的工具调用**（可并行）、**Rerank 的 Cross-Encoder**（候选集太大）、**检索召回 K 太大**、**System Prompt 太长导致 prefill 慢**、**多轮循环次数过多**。
  3. 对比 **token 数分布**，找出谁在烧 token（往往是工具返回值和历史对话）。
- **必要监控指标**：
  - 业务层：任务成功率、平均步数、平均 token 消耗、人工接管率、用户采纳率。
  - 性能层：P50 / P95 / P99 延迟、TTFT、吞吐、错误率、429 率。
  - 质量层：检索命中率、Faithfulness、拒答率、格式解析失败率。
  - 成本层：每请求成本、每日 token 消耗、模型分布。
- **🟡 回放分析（Replay）**：保存完整输入输出，出问题后能重放那次执行。**这是 Agent 调试和传统断点调试最大的区别** —— Agent 是概率系统，同样的输入不一定同样的输出，只能靠日志和回放。

**Q1：手撕 Self-Attention（PyTorch）**

```python
import torch
import torch.nn as nn
import math

class SelfAttention(nn.Module):
    def __init__(self, d_model):
        super().__init__()
        self.d_model = d_model
        self.W_q = nn.Linear(d_model, d_model, bias=False)
        self.W_k = nn.Linear(d_model, d_model, bias=False)
        self.W_v = nn.Linear(d_model, d_model, bias=False)

    def forward(self, x, mask=None):
        # x: (batch, seq_len, d_model)
        Q, K, V = self.W_q(x), self.W_k(x), self.W_v(x)
        scores = Q @ K.transpose(-2, -1) / math.sqrt(self.d_model)  # (B, n, n)
        if mask is not None:
            scores = scores.masked_fill(mask == 0, float('-inf'))
        attn = torch.softmax(scores, dim=-1)
        return attn @ V
```

**要点（边写边说）**：`K.transpose(-2,-1)` 只转最后两维；除以 `sqrt(d_k)`；causal mask 用上三角 mask + `masked_fill(-inf)`（不能填 0，因为 softmax(0) 仍有权重）；softmax 沿最后一维。

**Q2：手撕 Multi-Head Attention（PyTorch）**

```python
class MultiHeadAttention(nn.Module):
    def __init__(self, d_model, num_heads):
        super().__init__()
        assert d_model % num_heads == 0
        self.d_model, self.h = d_model, num_heads
        self.d_k = d_model // num_heads
        self.W_qkv = nn.Linear(d_model, 3 * d_model, bias=False)
        self.W_o = nn.Linear(d_model, d_model, bias=False)

    def forward(self, x, mask=None):
        B, n, _ = x.shape
        qkv = self.W_qkv(x)                                  # (B, n, 3*d)
        q, k, v = qkv.chunk(3, dim=-1)
        # 分头: (B, n, d) -> (B, h, n, d_k)
        q = q.view(B, n, self.h, self.d_k).transpose(1, 2)
        k = k.view(B, n, self.h, self.d_k).transpose(1, 2)
        v = v.view(B, n, self.h, self.d_k).transpose(1, 2)
        scores = q @ k.transpose(-2, -1) / math.sqrt(self.d_k)
        if mask is not None:
            scores = scores.masked_fill(mask == 0, float('-inf'))
        out = torch.softmax(scores, dim=-1) @ v           # (B, h, n, d_k)
        out = out.transpose(1, 2).contiguous().view(B, n, self.d_model)
        return self.W_o(out)
```

**要点**：四步 —— 分头（`view` + `transpose`）、算注意力、拼接（`transpose` + `contiguous().view`）、输出投影。**`contiguous()` 不能少**，否则 `view` 会报错。

**Q3：手撕 RoPE（旋转位置编码）—— 字节/阿里必考**

```python
class RotaryPositionEmbedding(nn.Module):
    def __init__(self, dim, max_len=2048, base=10000):
        super().__init__()
        # theta_i = base^(-2i/dim), i = 0..dim/2-1
        inv_freq = 1.0 / (base ** (torch.arange(0, dim, 2).float() / dim))
        self.register_buffer('inv_freq', inv_freq)   # (dim/2,)

    def forward(self, q, k, seq_len):
        # q, k: (B, h, n, d)
        t = torch.arange(seq_len, device=q.device).float()
        freqs = torch.outer(t, self.inv_freq)        # (n, d/2)
        emb = torch.cat([freqs, freqs], dim=-1)      # (n, d)
        cos, sin = emb.cos()[None, None], emb.sin()[None, None]

        def rotate_half(x):
            x1, x2 = x[..., :x.shape[-1] // 2], x[..., x.shape[-1] // 2:]
            return torch.cat([-x2, x1], dim=-1)

        q_rot = q * cos + rotate_half(q) * sin
        k_rot = k * cos + rotate_half(k) * sin
        return q_rot, k_rot
```

**要点**：RoPE 只作用在 Q 和 K 上（V 不动）；`rotate_half` 是配对旋转 `(x1,x2) -> (-x2,x1)`；**关键性质是内积只依赖相对位置**。

**Q4：手撕 LayerNorm / RMSNorm**

```python
class LayerNorm(nn.Module):
    def __init__(self, d_model, eps=1e-6):
        super().__init__()
        self.gamma = nn.Parameter(torch.ones(d_model))
        self.beta = nn.Parameter(torch.zeros(d_model))
        self.eps = eps
    def forward(self, x):
        mean = x.mean(-1, keepdim=True)
        var = x.var(-1, unbiased=False, keepdim=True)
        return (x - mean) / torch.sqrt(var + self.eps) * self.gamma + self.beta

class RMSNorm(nn.Module):
    def __init__(self, d_model, eps=1e-6):
        super().__init__()
        self.weight = nn.Parameter(torch.ones(d_model))
        self.eps = eps
    def forward(self, x):
        rms = torch.sqrt(x.pow(2).mean(-1, keepdim=True) + self.eps)
        return x / rms * self.weight
```

**要点**：LayerNorm 在**最后一维**归一化（不是 batch 维）；RMSNorm 去掉 mean，只保留缩放，少一个参数、更快。

**Q5：手撕 KV Cache 的自回归生成（🟡 高频）**

```python
# 核心思路：prefill 阶段算全序列 KV 并缓存，decode 阶段只算新 token 的 Q
def generate_with_kv_cache(model, input_ids, max_new_tokens):
    past_kv = None
    cur = input_ids
    for _ in range(max_new_tokens):
        logits, past_kv = model(cur, past_key_values=past_kv, use_cache=True)
        next_id = logits[:, -1, :].argmax(-1)   # 贪心
        input_ids = torch.cat([input_ids, next_id[:, None]], dim=-1)
        cur = next_id[:, None]                   # 下一轮只喂 1 个 token
        if next_id.item() == EOS: break
    return input_ids
```

**要点**：`use_cache=True` 时第一轮（prefill）输入完整序列，之后每轮**只输入 1 个 token**；第 t 步的复杂度从 O(t·d) 降到 O(d)。

**Q6：手撕 Top-K / Top-P 采样（🟡）**

```python
def top_k_top_p_filtering(logits, top_k=0, top_p=1.0):
    # logits: (vocab,)
    if top_k > 0:
        kth = torch.topk(logits, top_k)[0][..., -1, None]
        logits = torch.where(logits < kth, torch.full_like(logits, -float('inf')), logits)
    if top_p < 1.0:
        sorted_logits, sorted_idx = torch.sort(logits, descending=True)
        probs = torch.softmax(sorted_logits, dim=-1)
        cum = torch.cumsum(probs, dim=-1)
        # 保留累计概率刚超过 top_p 的最小集合（注意右移一位，保证至少留一个）
        remove = cum - probs > top_p
        sorted_logits[remove] = -float('inf')
        logits = sorted_logits.scatter(0, sorted_idx, sorted_logits)
    return logits
```

**要点**：top-p 的边界处理容易写错 —— 要保证**至少保留 1 个 token**；先排序、算累计、找切点、再映射回原顺序。

### 6.2 🔴 必考：RAG / Agent 模块手撕

**Q7：实现一个文本切分（Chunking）函数**

```python
def chunk_text(text, chunk_size=512, overlap=64, separators=("\n\n", "\n", "。", " ")):
    """按分隔符优先递归切分，超长再硬切；带 overlap。"""
    if len(text) <= chunk_size:
        return [text] if text.strip() else []

    for sep in separators:
        if sep in text:
            parts = text.split(sep)
            break
    else:
        parts = [text[i:i + chunk_size] for i in range(0, len(text), chunk_size - overlap)]

    chunks, buf = [], ""
    for p in parts:
        piece = p + (sep if sep else "")
        if len(buf) + len(piece) <= chunk_size:
            buf += piece
        else:
            if buf: chunks.append(buf)
            # 处理单个 part 就超过 chunk_size 的情况
            while len(piece) > chunk_size:
                chunks.append(piece[:chunk_size])
                piece = piece[chunk_size - overlap:]
            buf = piece
    if buf: chunks.append(buf)
    return chunks
```

**要点**：**递归字符切分（RecursiveCharacterTextSplitter）** 是工业界默认策略 —— 优先按段落切，不行按句子，再不行按字符。讲清楚"overlap 是为了防止关键信息跨块被切断"。

**Q8：实现余弦相似度 + Top-K 检索**

```python
import numpy as np

def cosine_topk(query_vec, doc_matrix, k=5):
    """
    query_vec: (d,)
    doc_matrix: (N, d)
    返回 top-k 的 (索引, 分数)
    """
    q = query_vec / (np.linalg.norm(query_vec) + 1e-10)
    d = doc_matrix / (np.linalg.norm(doc_matrix, axis=1, keepdims=True) + 1e-10)
    sims = d @ q                                  # (N,) 已归一化，内积即余弦
    idx = np.argpartition(-sims, min(k, len(sims) - 1))[:k]   # O(N) 部分排序
    idx = idx[np.argsort(-sims[idx])]                        # 只对 k 个排序
    return list(zip(idx.tolist(), sims[idx].tolist()))
```

**要点**：归一化后用内积等价于余弦；`argpartition` 是 O(N) 的 top-k，比全排序 O(N log N) 快，这是加分点。生产环境用 FAISS/向量库。

**Q9：实现 BM25（🟡 高频）**

```python
from collections import Counter
import math

class BM25:
    def __init__(self, corpus, k1=1.5, b=0.75):
        self.k1, self.b = k1, b
        self.docs = [d.lower().split() for d in corpus]
        self.N = len(self.docs)
        self.avgdl = sum(len(d) for d in self.docs) / max(self.N, 1)
        self.tf = [Counter(d) for d in self.docs]
        df = Counter()
        for d in self.docs:
            df.update(set(d))
        self.idf = {t: math.log((self.N - n + 0.5) / (n + 0.5) + 1)
                    for t, n in df.items()}

    def score(self, query, i):
        s, dl = 0.0, len(self.docs[i])
        for t in query.lower().split():
            if t not in self.tf[i]: continue
            f = self.tf[i][t]
            s += self.idf.get(t, 0.0) * f * (self.k1 + 1) / (
                f + self.k1 * (1 - self.b + self.b * dl / self.avgdl))
        return s

    def search(self, query, k=5):
        scores = [(i, self.score(query, i)) for i in range(self.N)]
        return sorted(scores, key=lambda x: -x[1])[:k]
```

**要点**：能写出公式 `IDF · tf·(k1+1) / (tf + k1·(1-b+b·|d|/avgdl))` 并解释 `k1`（词频饱和）和 `b`（长度归一化）的含义就足够了。

**Q10：实现 RRF 融合（🟡）**

```python
def rrf_fusion(rankings, k=60, top_n=10):
    """rankings: List[List[doc_id]]，每路的排序结果"""
    scores = {}
    for ranking in rankings:
        for rank, doc_id in enumerate(ranking, start=1):
            scores[doc_id] = scores.get(doc_id, 0.0) + 1.0 / (k + rank)
    return sorted(scores.items(), key=lambda x: -x[1])[:top_n]
```

**要点**：RRF 只用**排名**不用分数，天然规避了两路分数不可比的问题；`k=60` 是原论文的经验值。

**Q11：实现一个带 max_steps、工具注册表、异常重试的简易 ReAct 循环（🔴 大题）**

```python
import json, time, logging
from typing import Callable

log = logging.getLogger(__name__)

class ToolRegistry:
    def __init__(self):
        self._tools: dict[str, dict] = {}

    def register(self, name: str, description: str, schema: dict, fn: Callable):
        self._tools[name] = {"description": description, "schema": schema,
                             "fn": fn, "fail_count": 0}

    def specs(self):
        return [{"name": n, "description": t["description"],
                 "parameters": t["schema"]} for n, t in self._tools.items()]

    def call(self, name: str, args: dict, max_retry: int = 2) -> str:
        if name not in self._tools:
            # 工具幻觉拦截：返回结构化错误，让模型重新选择
            return json.dumps({"error": "TOOL_NOT_FOUND",
                               "available": list(self._tools)}, ensure_ascii=False)
        tool = self._tools[name]
        for attempt in range(max_retry + 1):
            try:
                return str(tool["fn"](**args))
            except (TypeError, ValueError) as e:
                # 可修复错误：把摘要反馈给模型
                return json.dumps({"error": "BAD_ARGS", "hint": str(e),
                                   "schema": tool["schema"]}, ensure_ascii=False)
            except Exception as e:
                if attempt == max_retry:
                    return json.dumps({"error": "TOOL_FAILED", "detail": str(e)},
                                      ensure_ascii=False)
                time.sleep(2 ** attempt)   # 指数退避
        return "{}"


def react_loop(question, tools: ToolRegistry, llm, max_steps=8,
               max_tokens_budget=50000, max_repeat=2):
    history, seen = [], {}
    used_tokens = 0

    for step in range(max_steps):
        prompt = build_prompt(question, tools.specs(), history)
        out, tokens = llm(prompt)
        used_tokens += tokens

        # 终止条件 1：模型给出最终答案
        if "Final Answer:" in out:
            return out.split("Final Answer:", 1)[1].strip()

        thought, action, args = parse(out)
        if not action:
            history.append(("解析失败，请严格按格式输出", ""))
            continue

        # 终止条件 2：重复动作检测
        key = (action, json.dumps(args, sort_keys=True))
        seen[key] = seen.get(key, 0) + 1
        if seen[key] > max_repeat:
            history.append(("检测到重复调用，请换一种方式或给出最终答案", ""))
            continue

        obs = tools.call(action, args)
        history.append((thought, obs))

        # 终止条件 3：token 预算
        if used_tokens > max_tokens_budget:
            return summarize(history)   # 超预算强制收尾

    # 终止条件 4：达到最大步数
    return summarize(history)
```

**要点（这是面试官最想听的）**：① 工具白名单拦截幻觉工具名；② 错误分类处理（可修复 vs 可重试 vs 不可恢复）；③ **重复动作检测**防死循环；④ **四种终止条件**；⑤ token 预算；⑥ 结构化错误返回给模型而不是裸堆栈。**能把这六点讲全，这道题就是满分。**

### 7.0 🔴 必考：先搞懂 APC 三层架构

**半导体晶圆厂 AI 落地的主战场是 APC（Advanced Process Control，先进过程控制）**，它由三层组成：

| 层级 | 技术 | 功能 |
|---|---|---|

### 7.1 🔴 必考：虚拟量测（Virtual Metrology, VM）

**Q：什么是虚拟量测？它解决什么问题？**

- **定义**：VM 是**用设备传感器数据（process equipment sensor data）预测晶圆质量特征**的技术，不需要实际使用量测仪器。
- **输入**：机台传感器时序信号 —— RF Power（射频功率）、Pressure（腔体压力）、Gas Flow（气体流量）、Chamber Temperature（腔体温度）、Etch Time（刻蚀时间）等。
- **输出 / 预测目标**：CD（Critical Dimension，关键尺寸）、膜厚（Film Thickness）、方阻、电学特性（电阻率、击穿电压）。
- **为什么需要 VM**：
  1. **量测是瓶颈**：量测机台昂贵、产能有限，且只能抽检（sampling），无法 100% 全检。
  2. **量测有延迟**：物理量测结果要等几十分钟到几小时，来不及做实时控制。
  3. **VM 实现 100% 全检 + 实时预测**，从而支持 inline 控制（跑完一片就能预测、就能决定下一片参数）。
- **评价指标（🔴 必答）**：
  - **MAE（Mean Absolute Error）**、**RMSE（Root Mean Squared Error）** —— 预测精度。
  - **R²（决定系数）** —— 拟合优度，产线上一般要求 **R² > 0.9**，好的模型 > 0.95。
  - **预测区间（Prediction Interval）/ 置信度** —— 工业场景很关键，工程师需要知道"这个预测有多可信"。
  - **🟡 加分**：还有 **VM 的可用率（VM availability）** 和 **模型漂移监控指标**。
- **常用模型**：
  - **PLS（Partial Least Squares，偏最小二乘回归）**：传统产线标配。原因是传感器变量高度共线（multicollinearity），样本量小（几百片），且需要**可解释性**（工程师要看系数）。PLS 天然处理共线性、给出 VIP（Variable Importance in Projection）分数。
  - **树模型（Random Forest / XGBoost / LightGBM）**：能捕捉非线性，特征重要性可解释，小样本也稳，是当前产线主流。
  - **深度学习（LSTM / GRUB / 1D-CNN / Transformer）**：适合传感器时序信号，能捕捉时间动态。但需要更多数据，可解释性差。
  - **🟡 追问：为什么不用 LSTM 而用 PLS？** —— 样本量小（几百片 vs 需要上万条）、需要可解释性（工艺工程师要能理解并在异常时介入）、推理延迟要求（边缘端 50ms）、部署和维护成本（PLS 是几个矩阵乘，LSTM 要 GPU）。**这是体现你懂工业约束的关键回答。**
- **VM 与 R2R 的关系（🟡 高频追问）**：**VM 是 R2R 的使能技术。** 没有 VM 时，R2R 必须等物理量测结果，控制周期 = 一个量测周期（慢，且只有抽检的片子有反馈）；有了 VM，每片晶圆都能得到预测值，R2R 能做到**每片闭环**（wafer-to-wafer control），控制精度和响应速度都大幅提升。
- **🔴 追问：VM 模型漂移了怎么办？**（几乎必问）
  - **检测**：监控预测残差（predicted vs actual，用抽检片校准）的分布漂移；用统计过程控制（CUSUM / EWMA）做残差监控；PSI / KL 散度监控输入特征分布。
  - **应对**：① 定期用新数据**增量重训 / 在线学习**；② **漂移补偿（bias update）** —— 用最近的实测片算预测偏差，加到预测值上（最简单有效）；③ **触发重训的门槛** —— 残差超过阈值或漂移检测报警时触发；④ **模型版本管理 + 影子模式**（新模型并行跑不参与控制，对比稳定后切换）。
  - **🟡 高分点**：要提到「**换机台/换腔体/换保养周期后模型必须重新标定**」—— 这是半导体特有的，一个模型不能跨 chamber 直接用。

参考：[Virtual Metrology in Semiconductor Manufacturing（ScienceDirect）](https://www.sciencedirect.com/science/article/pii/S095741742400424X)、[Chapter 1: Wafer Process Statistical Control（Process Informatics Dojo）](https://yusukehashimotolab.github.io/AI-Knowledge-Notes/knowledge/en/PI/semiconductor-manufacturing-ai/chapter-1.html)

### 7.2 🔴 必考：APC / Run-to-Run 控制

**Q：什么是 R2R 控制？EWMA 控制器怎么工作？**

- **定义**：R2R（Run-to-Run）是一种**自适应控制方法**，把**前一片（或前一批）晶圆的量测结果反馈回来**，调整下一片（批）的工艺条件。控制周期是「run」（一次工艺），不是实时闭环（那是 real-time control）。
- **EWMA 控制器公式（必背）**：
  ```
  u_k = u_{k-1} + K · (T − y_k)
  ```
  - `u_k`：第 k 次 run 的控制输入（工艺参数，如刻蚀时间）
  - `y_k`：第 k 次 run 的量测值（或 VM 预测值）
  - `T`：目标值（target）
  - `K`：控制增益（control gain），`0 < K < 1`
  - 本质是**积分控制（Integral Control）**：用误差累积来驱动输入，`K` 就是积分增益。
- **`K` 的权衡（🔴 面试重点）**：
  - **K 大** → 响应快，但**噪声放大**，容易震荡（over-correction）。
  - **K 小** → 平稳，但**对工艺漂移响应慢**，可能长时间超标。
  - 经验：`K` 取 0.1–0.5（常见 0.3 或 0.5），需结合工艺噪声水平和漂移速率调优。
  - **🟡 加分**：工程上还有 **dEWMA（double EWMA）** 处理带漂移的过程，以及**约束优化**（不能突破物理极限，如刻蚀时间不能超过 90s，需要 `clip`）。
- **R2R 在半导体各工序的应用**：
  - **Etching（刻蚀）**：调刻蚀时间控制 CD
  - **CVD / PVD 沉积**：调沉积时间控制膜厚
  - **CMP（化学机械抛光）**：调抛光时间控制平坦度
  - **Lithography（光刻）**：调曝光剂量（dose）和焦距（focus）控制线宽
- **反馈控制 vs 前馈控制（🔴 对比题）**：
  - **反馈（Feedback）**：测量输出后调整输入。精度高但**滞后一轮**（first wafer 有偏差）。
  - **前馈（Feedforward）**：测量**输入侧**的扰动（如 incoming 膜厚），提前补偿。**能消除 first-wafer effect**，但依赖扰动可测。
  - 工业上通常是**前馈 + 反馈组合**：前馈处理已知扰动，反馈处理模型误差和慢漂移。
- **🟡 R2R 与 SPC 的区别**：
  - **SPC（Statistical Process Control）** 是**监控**（monitoring）：判断过程是否受控，异常就报警，让工程师介入。是**被动**的。
  - **R2R / APC** 是**控制**（control）：自动调整参数把输出拉回目标。是**主动**的。
  - **关系**：SPC 管"报警"，APC 管"自动修正"。现代产线两者结合 —— APC 负责常规漂移补偿，SPC 负责检测 APC 也处理不了的异常。
- **🟡 为什么半导体特别需要 R2R**：① 单件生产（每批可能只有 25 片，甚至单片刻蚀），样品量小；② 工艺漂移慢但持续（腔体老化、耗材磨损、聚合物沉积）；③ 量测昂贵且慢，不能实时全检；④ 工艺窗口窄，几 nm 的偏差就影响良率。

参考：[Run-to-Run CD Control（APMonitor）](https://apmonitor.com/apps/litho-etch-r2r/instructions.php)

### 7.3 🔴 必考：FDC（故障检测与分类）

**Q：FDC 是什么？怎么检测异常？**

- **定义**：FDC（Fault Detection and Classification）**实时采集设备传感器数据和工艺参数**，判断设备/工艺是否处于正常状态，异常时报警（alarm / interlock）。
- **输入**：机台传感器 trace —— 温度、压力、流量、RF 反射功率、OES 光谱、振动、电流等，采样率可达 10 Hz 甚至更高（一台设备可能几百个传感器）。
- **核心难点**：
  1. **什么是"正常"要先定义** —— 工艺工程师必须先决定正常轨迹的形态（这是 FDC 最难的工程问题）。
  2. **正常也有波动** —— 不同 recipe、不同产品、不同腔体、保养前后基线都不同。
  3. **类别极度不平衡** —— 异常样本极少（可能 < 0.1%）。
  4. **误报的代价很高** —— 误报（False Alarm）会导致不必要的停机，工程师会因此失去对系统的信任而关掉报警。**这是半导体 AI 落地最大的组织障碍。**
- **方法（按复杂度递进，面试要能说出这一层）**：
  1. **传统 SPC**：3-sigma 控制限、Western Electric Rules、控制图（Control Chart）。
  2. **多变量统计过程控制（MSPC）**：
     - **PCA + T² 统计量 + SPE/Q 统计量** —— 必答！`T²` 检测主元空间内的偏离（反映过程变化幅度），`SPE`（Squared Prediction Error，也称 Q 统计量）检测残差空间的异常（反映变量间相关结构被破坏，即出现了新的关系模式）。两者结合才能覆盖两类异常。
     - **PLS / 动态 PCA（DPCA）** 处理自相关。
  3. **机器学习**：Isolation Forest、One-Class SVM、Local Outlier Factor（无监督/半监督，因为异常标签少）。
  4. **深度学习**：Autoencoder（重构误差做异常分数）、LSTM-AE、VAE、Transformer-based 时序异常检测。
  5. **trace 特征工程（🔴 高频追问）**：
     - **时域特征**：均值、标准差、最大/最小值、峰峰值、斜率、积分（面积）、到达稳态的时间、过冲量（overshoot）。
     - **频域特征**：FFT 主频、频谱能量分布（RF 功率的频谱能反映匹配网络问题）。
     - **统计特征**：偏度、峰度、分位数。
     - **分段特征**：把 trace 按 step 切分（semiconductor recipe 天然分 step），每个 step 单独提特征。
- **类别不平衡处理**：SMOTE / ADASYN（合成少数类）、`class_weight='balanced'`、Focal Loss、下采样、**异常检测范式（不用分类，用无监督异常分数）**。
- **🔴 误报（FAR, False Alarm Rate）与漏报（FDR / Miss Rate）的权衡**：
  - 这是 FDC 面试的必答 trade-off：降低误报门槛 → 漏报减少但误报增加，工程师会关掉报警；提高门槛 → 误报少但可能漏掉真实故障，造成大批报废。
  - **实践做法**：① 用**代价敏感学习**（给漏报更高的损失权重，因为报废成本远高于一次停机检查）；② **分级报警**（warning / alarm / interlock 三级，不同级别不同响应）；③ **报警聚合与去重**（避免一个故障触发 50 条报警，工程师会麻痹）；④ **持续监控工程师的采纳率**（报警被采纳的比例）。
  - **🔴 高分句**：「FDC 的挑战不只是算法精度，更是**工程师信任**。一个 95% 准确但每天误报 20 次的系统，会被关掉；一个 85% 准确但报警都能被验证为真的系统，会活下来。」

参考：[晶圆厂 APC 完全指南](https://ai-mst.com/insight/apc-vm-r2r-fdc-guide/)

### 7.4 🟡 加分：良率分析与 Wafer Map

**Q：良率分析怎么做？Wafer Map 的缺陷图案怎么分类？**

- **良率损失的两大类**：
  - **随机缺陷（Random Defects）**：颗粒污染（particle）、针孔等，空间上随机分布，通常用 Poisson / Murphy 模型建模，与**缺陷密度 D 和芯片面积 A** 相关（`Y = e^{-AD}` 是 Poisson 良率模型）。
  - **系统缺陷（Systematic Defects）**：由工艺/设备/设计问题导致的**有图案的**缺陷，空间上聚集，是良率提升的主要攻坚对象。
- **Wafer Map Pattern 分类（典型图案，要能说出这些名字）**：
  - **Center / Donut（中心/圆环）** —— 通常与旋涂、CMP、刻蚀均匀性有关
  - **Edge / Ring（边缘环状）** —— 与边缘效应、聚焦、温度梯度有关
  - **Scratch（划痕）** —— 机械搬运、CMP 划伤
  - **Zoning / Sector（分区/扇形）** —— 与腔体气流、喷淋头方向性有关
  - **Radial（放射状）** —— 与旋转工艺有关
  - **Local Cluster（局部聚集）** —— 单个 die 集中失效
  - **Repeat / Repeater（重复图案）** —— 与掩模版（reticle）缺陷有关，**这个尤其重要，因为直接指向光刻**
- **Commonality Analysis（共性分析）**：把失效的晶圆按**机台、腔体、recipe、工序、时间、批次**分组，统计哪一组的失效率显著高于平均。这是良率工程师最核心的工具，也是"根因分析"的标准方法。**面试时要能说出这个名词。**
- **机器学习应用**：Wafer Map 图案分类（CNN，输入是 bin map 图像）、缺陷聚类（DBSCAN 找聚集区）、缺陷与最终良率的相关性建模、**WRA（Wafer Risk Analysis，晶圆履历分析）** —— 把每片晶圆经过的所有工序、机台、参数串起来，回溯找出良率症结。
- **🟡 相关工具/系统**：**YMS（Yield Management System）**、**MES（Manufacturing Execution System）**、**SPC 系统**、**DMS（Defect Management System）**。

参考：[晶圆 Fab 厂 YE 工程师常见面试问题（与非网）](https://www.eefocus.com/article/1735566.html)

### 7.5 🔴 必考：时序数据与传感器信号

**Q：半导体设备传感器数据有什么特点？建模要注意什么？**

- **特点（面试要能数出来）**：
  1. **多变量、高维度**：一台设备几百个传感器。
  2. **高采样率 + 长时长**：10 Hz 采样、单步工序几十分钟，一条 trace 几万个点。
  3. **强共线性**：很多传感器测的是同一物理量的不同侧面（多个温度探头）。
  4. **分 step 结构**：recipe 天然把一次工艺分成多个 step（抽气、起辉、主刻蚀、过刻蚀、吹扫），每个 step 的物理机制不同。**🔴 高分点：必须按 step 分段提特征，不能把整条 trace 当一个序列。**
  5. **传感器漂移（drift）**：传感器本身会老化漂移，需要在保养时做校准。
  6. **批次效应（batch effect）**：不同机台、腔体、时间段的基线不同，需要归一化。
  7. **标签稀缺且昂贵**：需要工程师标注，异常样本极少。
  8. **数据量巨大**：全 Fab 每天产生的 trace 数据是 TB 级，存储和处理都是挑战。
- **建模注意事项**：
  - **缺失值**：传感器掉线、通信丢包，需要插值（线性 / 前向填充）或 mask 标记。
  - **采样率对齐**：不同传感器采样率不同，需要重采样到统一时序。
  - **归一化**：按机台/腔体分别标准化（z-score），不能用全局均值。
  - **窗口切分**：滑窗提特征，窗口大小要匹配物理过程的特征时间尺度。
  - **数据泄漏（🔴 常见坑）**：按时间随机切分训练/测试集会泄漏（同一批次的数据同时出现在训练和测试）。**正确做法是按时间切分（time-based split）或按批次/机台分组切分（GroupKFold）** —— 这是面试官很爱问的细节。
- **时序基础模型（Time Series Foundation Models）**：TimeGPT、**PatchTST**、**iTransformer**、TimesNet、Moirai、Chronos。**🟡 面试可能的追问：这些模型在半导体场景有用吗？**
  - **诚实的高分回答**：有价值但**不能直接用**。① 它们是通用预训练，对半导体特有的 step 结构和物理约束没有先验；② 工业数据是私有的，无法贡献到预训练；③ 零样本预测精度通常不如针对单一工艺训的 GBDT；④ **但可以作为特征提取器（frozen encoder）或在少样本场景下做微调**，这是比较现实的落地路径。

### 7.6 🔴 必考：知识库问答与工艺文档检索（RAG 在半导体）

**Q：半导体场景的知识库问答，和通用 RAG 有什么不同？**

- **文档特殊性（决定技术方案）**：
  1. **大量表格**：配方表（Recipe）、参数规格、量测数据、设备清单。**表格必须结构化处理**（转 Markdown / JSON，保留行列语义），直接 OCR 成流水文本会导致模型读错行列。需要 **Layout-aware 解析**（如 LayoutLM、PP-Structure、MinerU）。
  2. **图纸 / 版图 / 界面截图**：需要**多模态 RAG**（视觉 embedding + caption 生成 + 保留页码和 bbox 以便回溯）。
  3. **专业缩写和同义词极其密集**：CD、APC、R2R、FDC、OES、PVD、CVD、CMP、RCA、DOE、SPC、CPK、SECS/GEM、MES、EAP…需要在检索层加**同义词/术语表扩展**，或在 embedding 前做术语标准化。
  4. **版本与生效日期强相关**：SOP 和工艺规范有多个版本，**引用失效版本是严重事故**。必须保留 metadata（版本号、生效日期、作废标记）并在检索时**强制过滤**。
  5. **强权限与保密**：不同部门/客户/代工项目的数据不能互串。**检索必须做 metadata filtering（按项目、部门、密级、客户打标）**，且权限校验要在检索层之前（不是检索后在 prompt 里说"不要泄露"）。
- **🔴 幻觉在工艺场景的后果**：通用场景答错了是用户体验问题；工艺场景答错了可能导致**误操作设备、批量报废、安全事故**。所以：
  - 必须**强制引用**（每个结论后面跟原文片段和文档编号）。
  - 必须支持**拒答**（"文档中未找到相关内容"要成为正常输出，而不是失败）。
  - 高风险查询必须**转人工**（涉及设备参数修改、安全规程）。
  - 建议接入 **人在环路审批**（见第 4.2 节）。
- **🟡 表格问答的专门方案**：**Text-to-SQL**（把自然语言转成 SQL 查结构化数据表）而不是把表格塞进 prompt。半导体场景大量数据在数据库里（MES / YMS / SPC），Text-to-SQL 比 RAG 更合适。但要强调：**SQL 必须经过 schema 校验和只读权限限制，且生成的 SQL 要先给人看**。

### 7.7 🔴 必考：Agent / LLM 在半导体场景怎么落地

**Q：你觉得 LLM / Agent 在晶圆厂能做什么？边界在哪？**

- **能做的（按可行性排序，这个排序本身就是加分点）**：
  1. **知识问答助手（最成熟）**：工艺文档、SOP、设备手册、故障处理手册的检索问答。技术门槛低、风险可控（只读）、价值明确（新人培训、工程师查资料）。
  2. **报告生成**：把 FDC 报警、良率数据、SPC 图表自动生成日报/周报，节省工程师写报告的时间。
  3. **RCA（Root Cause Analysis，根因分析）辅助 Agent**：**这是最有想象力的方向。** 给一个良率异常，Agent 自动去查相关批次的机台履历、传感器 trace、量测数据、历史相似 case，生成假设列表（"可能是 3 号刻蚀机腔体 B 的 RF 匹配网络漂移"）供工程师验证。**关键是「辅助」而不是「决策」** —— Agent 提假设，工程师验证。
  4. **报警处置助手**：FDC 报警时给出**历史相似报警的处理记录**和推荐动作（基于 case-based reasoning + RAG）。
  5. **设备维保助手**：设备报警代码 → 排查步骤 → 备件信息。
  6. **代码/脚本生成**：帮工程师写数据处理脚本、SQL、可视化代码。
- **做不了的 / 边界（🔴 这题答好非常加分）**：
  1. **实时控制回路（real-time control）不能用 LLM**：延迟（LLM 秒级 vs 控制要求 50ms）、确定性（控制必须可复现可证明）、可靠性（不能有 1% 的幻觉率）都不满足。**实时控制必须用传统模型（PLS/GBDT/物理模型）。**
  2. **VM 预测不适合用 LLM**：VM 是回归问题，需要精确数值和小样本，PLS/树模型更好、更快、更可解释。
  3. **安全联锁（interlock）绝不能用 LLM**：这是功能安全问题，必须用确定性逻辑。
  4. **LLM 不擅长数值计算和严格逻辑推理**，涉及参数计算要用工具（Function Calling 调计算器/仿真器），而不是让模型算。
- **🔴 为什么传统 ML 仍然占主导（面试常问）**：
  - **数据量小**：一个工艺可能只有几百片数据，LLM 微调不现实，传统 ML 更合适。
  - **可解释性刚需**：工艺工程师必须能理解模型为什么这么判，才能信任并采纳。PLS 系数、树模型特征重要性都是可解释的；LLM 是黑盒。
  - **延迟要求**：边缘端 50ms，LLM 做不到。
  - **确定性**：产线要可审计、可复现，LLM 的概率性输出不符合要求。
  - **成本**：Fab 里有几百台设备、几千个工艺，都用 LLM 推理成本不可承受。
  - **验证困难**：传统模型可以用统计方法验证（置信区间、交叉验证），LLM 的输出难以严格验证。
- **🟡 与现有系统的集成（追问点）**：
  - **SECS/GEM**：半导体设备通信标准协议，SCADA / EAP（Equipment Automation Program）通过它采集数据和下发指令。
  - **MES / EAP / SPC / YMS / FDC / RMS（Recipe Management System）**：Agent 要接这些系统的 API。
  - **数据不能出内网**：必须私有化部署（Qwen / DeepSeek 本地部署，见第 5.8 节）。
  - **边缘 AI vs 云端 AI（🟡 追问）**：边缘（设备旁）延迟低、数据不出厂、可靠性高，但算力受限、模型更新麻烦；云端算力强、易更新，但延迟和数据处理合规是问题。**实践：控制/检测放边缘，知识问答/报告生成/RCA 放云端。**

### 7.8 🟡 加分：面试官常见追问链

> 半导体 AI 岗的追问往往是「连环炮」，提前想好每一层的应对。

**追问链 1：VM 方向**
```
VM 用什么模型？ → 为什么不用深度学习？
→ 模型上线后精度掉了怎么办？ → 怎么判断是模型问题还是工艺真的变了？
→ 怎么让工艺工程师信任这个预测值？ → 预测置信区间怎么给？
→ 如果 VM 预测错了，R2R 用它做控制会怎样？ → 怎么设保护？
```
**最后两问的答案要点**：VM 预测错误会被 R2R 放大成整批偏差，所以必须 ① 给预测区间，区间过宽时**降级为不控制**（只用 SPC 监控）；② 设**控制幅度限制**（单次调整不超过工艺窗口的 X%）；③ 定期用实测片**校准 bias**；④ VM 的预测值和实测值偏差连续超标时**自动退出闭环控制**。

**追问链 2：FDC 方向**
```
怎么定义异常？ → 误报太多了怎么办？
→ 工程师把报警关了怎么办？ → 怎么衡量报警系统的价值？
→ 报警之间的关联怎么处理？（一个根因触发 50 条报警）
→ 怎么区分"设备真故障"和"工艺参数正常波动"？
```
**关键答案要点**：① 报警聚合（把关联报警归并成"事件"再展示）；② 分级（warning/alarm/interlock）；③ 追踪**报警采纳率**作为核心 KPI（不是准确率）；④ 用**工况上下文**区分（同一报警在不同 recipe 下含义不同）。

**追问链 3：RAG / 知识库方向**
```
文档里有表格和图纸怎么处理？ → 怎么保证不引用过期版本？
→ 怎么防止模型编造工艺参数？ → 如果有权限隔离怎么检索？
→ 怎么评估这个问答系统的效果？ → 工程师不用怎么办？
```
**关键答案要点**：① Layout-aware 解析 + 表格结构化；② 版本 metadata 硬过滤；③ 强制引用 + 拒答机制 + 高风险转人工；④ 检索层前置权限过滤；⑤ 评测用「Top-1 引用正确率」+「拒答正确率」+ 工程师采纳率；⑥ 落地策略是先做**只读、低风险、高频**的场景（查文档），积累信任后再上更复杂的能力。

**追问链 4：通用技术追问**
```
你们的 RAG 怎么评估？ → 离线指标涨了线上为什么掉？
→ 你怎么知道是检索的问题还是生成的问题？ → 怎么归因？
→ Prompt 改了一版怎么知道变好还是变坏？ → 有没有 CI？
→ 一个请求多少钱？怎么降？ → 缓存的命中率多少？语义缓存的阈值怎么定？
```
**这些是 2026 年的必考线**，回答框架见第 3.7、4.5、5.6、5.7 节。

## 第 8 节 · 答不上来会明显减分的概念

> 以下概念是**面试官默认你应该知道**的。答不上来会被直接判定为「没真正做过 / 只会用 API」，即使其他部分答得很好也会显著拉低评价。

### 8.1 减分级：核心原理（必须秒答）

| 概念 | 一句话标准答案 | 不知道的后果 |
|---|---|---|
| **Self-Attention 复杂度** | O(n²·d)，因为每个 token 要和所有 token 算相关性，产生 n×n 矩阵 | 算法岗直接判定基础不过关 |
| **为什么除以 √d_k** | 点积方差随维度线性增长，不缩放会把 softmax 推到饱和区导致梯度消失 | 高频送命题 |
| **KV Cache** | 缓存历史 token 的 K/V，decode 时只算新 token 的 Q，用显存换速度 | Agent/应用岗必问 |
| **KV Cache 显存公式** | `2 × L × n_kv_heads × d_head × seq_len × batch × bytes` | 让你现场估算显存时答不出来 |
| **权重显存估算** | 参数量 × 精度字节数（7B FP16 = 14 GB） | 同上 |
| **RoPE 的核心性质** | 旋转后两向量的内积只依赖**相对位置** | 字节/阿里必考 |
| **MHA / MQA / GQA** | 共享 KV 的头数递减，KV Cache 依次减小 | 百度二面原题 |
| **RMSNorm vs LayerNorm** | RMSNorm 去掉均值中心化，只保留缩放，更快更省 | 基础题 |
| **temperature / top-p 的作用范围** | 只改**解码策略**，不改模型知识 | 答"调 temperature 让模型答对"是硬伤 |
| **BPE 缓解 OOV 的机制** | 未登录词退化成子词/字节表示，而不是 [UNK] | Tokenizer 基础题 |

### 8.2 减分级：Agent 工程（没做过的人一眼看出）

| 概念 | 一句话标准答案 | 不知道的后果 |
|---|---|---|
| **Agent 的四种终止条件** | Final Answer / max_steps / 重复动作检测 / 不可恢复错误（+ 预算上限、用户中断） | 只答"模型说完了"= 没有工程视角 |
| **Observation 必须由谁生成** | 必须由执行器/工具生成，绝不能让模型续写 | 这是 Agent 设计的铁律 |
| **ReAct 与 CoT 的区别** | CoT 闭卷推理；ReAct 有外部工具反馈闭环 | 基础概念题 |
| **Function Calling 到底谁执行函数** | 模型只返回结构化调用请求，**宿主应用执行** | 误解成模型执行 = 安全意识缺失 |
| **API Key 应该放在哪** | 执行层注入，**永远不进上下文** | 安全题，答错很致命 |
| **MCP 解决什么问题** | 工具接入的**标准化**（AI 领域的 USB-C），不是模型能力 | 2025–2026 高频新题 |
| **LangGraph 相比 AgentExecutor 的价值** | 显式图编排，支持条件边、回环、人在环路、检查点 | 框架题 |
| **Agent 评测的 Transcript vs Outcome** | Agent 说的 ≠ 实际做的，必须验证环境状态 | 2026 必考，答不出来显得没做过评测 |
| **LLM Judge 的 Uncertain Escape Hatch** | 必须给 judge 一个「不确定」出口，否则等于允许它乱打分 | 评测题细节 |
| **人在环路（HITL）用在哪** | 高风险操作（删数据、发送、下单、改配方）前必须确认 | 生产化意识的标志 |

### 8.3 减分级：RAG

| 概念 | 一句话标准答案 | 不知道的后果 |
|---|---|---|
| **Recall@K / Precision@K / MRR / NDCG** | 能找到 / 找的纯度 / 首个正确排多前 / 排序质量 | 只能答"看召回率"= 明显没做过评测 |
| **RAGAS 四维度** | Faithfulness / Answer Relevancy / Context Relevancy / Context Recall | 同上 |
| **Bi-Encoder vs Cross-Encoder** | 双塔可预计算（快、用于召回）；交叉编码器要现算（准、用于 rerank） | Rerank 原理题 |
| **RRF 为什么好用** | 只用排名不用分数，规避两路分数不可比 | 混合检索融合的标准答案 |
| **HNSW vs IVF 取舍** | HNSW 换内存买速度和召回；IVF 换精度买内存和规模 | 向量库必考 |
| **chunk 太小 / 太大会怎样** | 太小语义不完整，太大噪声稀释注意力 | 基础题 |
| **embedding 升级怎么迁移** | 双写 + 版本化索引 + 灰度，**绝不原地覆盖** | 工程细节，答对很加分 |
| **父子块检索（Small-to-Big）** | 小块检索保精度，大块返回保上下文 | 进阶检索策略 |
| **HyDE 是什么** | 先让 LLM 生成假想答案，用假想答案的 embedding 去检索 | 查询改写进阶题 |
| **语义缓存的阈值** | 太松返回错误答案，太严命中率低，需要按业务调 | 缓存追问点 |

### 8.4 减分级：部署与工程

| 概念 | 一句话标准答案 | 不知道的后果 |
|---|---|---|
| **PagedAttention 到底优化了什么** | 优化**显存碎片和浪费**（提升并发），**不减少 KV Cache 绝对大小** | 这是最经典的易错题 |
| **Continuous Batching** | 迭代级调度，完成的请求立刻退出、新请求立刻插入 | vLLM 核心机制 |
| **Prefill 是 compute-bound，Decode 是 memory-bound** | 两阶段瓶颈不同，优化手段不同 | 讲推理优化时的基础框架 |
| **GPTQ vs AWQ** | GPTQ 逐层用 Hessian 补偿误差；AWQ 保护激活值大的重要通道 | 量化必考 |
| **投机解码为什么无损** | 用 rejection sampling，输出分布与大模型一致 | 概率题，答对加分多 |
| **TTFT / TPOT** | 首字延迟（prefill 决定）/ 每 token 延迟（decode 决定） | 性能指标基础 |
| **asyncio 里不能做什么** | 不能调阻塞同步 I/O（会卡死整个事件循环） | 后端岗硬伤 |
| **GIL 的影响** | CPU 密集用多进程，I/O 密集用协程 | Python 基础 |
| **Prompt Injection 的本质** | 模型难以区分「数据」和「指令」 | 安全必考 |
| **怎么定位 Agent 慢在哪** | 看 trace/span 瀑布图找最长 span；常见瓶颈是串行工具调用和 Cross-Encoder rerank | 可观测性题 |

### 8.5 减分级：半导体场景（仅对应行业）

| 概念 | 一句话标准答案 |
|---|---|
| **APC 三层架构** | FDC 感知 / VM 预测 / R2R 控制 |
| **VM 的定义和用途** | 用设备传感器数据预测晶圆质量，替代/减少物理量测 |
| **VM 的评价指标** | MAE / RMSE / R²，产线要求 R² > 0.9 |
| **EWMA R2R 公式** | `u_k = u_{k-1} + K(T − y_k)`，K 是控制增益 |
| **K 大 / K 小的权衡** | K 大响应快但易震荡；K 小平稳但对漂移响应慢 |
| **R2R 和 SPC 的区别** | SPC 是监控报警（被动），R2R 是自动修正（主动） |
| **PCA + T² / SPE** | T² 检测主元空间偏离，SPE 检测残差空间相关结构被破坏 |
| **FDC 的误报 vs 漏报** | 误报多工程师会关掉报警；漏报导致批量报废。漏报代价更高 |
| **Commonality Analysis** | 按机台/腔体/recipe/时间分组统计失效率，找异常组，是 RCA 的标准方法 |
| **什么是 step 分段特征** | recipe 把工艺分成多个 step，必须按 step 分别提特征 |
| **为什么实时控制不用 LLM** | 延迟（50ms vs 秒级）、确定性、可靠性、可解释性都不满足 |

### 3 天冲刺排期建议

**Day 1（打地基）**：知识点 1–7。上午原理（注意力/RoPE/KV Cache 手算），下午手撕（Self-Attention、MHA、RoPE、RMSNorm 各写一遍）。
**Day 2（核心战场）**：知识点 8–14。上午 Agent 核心（ReAct、Function Calling、MCP、LangGraph），下午 RAG（chunking、混合检索、rerank、评估指标），晚上手撕（ReAct 循环、RRF、BM25、余弦 top-k）。
**Day 3（工程 + 收口）**：知识点 15–20。上午部署与优化（PagedAttention、量化、显存估算、可观测性），下午把自己简历上**每个项目**用「业务背景 → 问题定义 → 技术选型 → 架构 → 数据与评测 → 成本控制 → 安全与可观测 → 上线迭代」这套结构讲三遍并录音复盘，晚上过一遍第 8 节的减分清单自我检查。

**面试当天的三个动作**：
1. 面试前 30 分钟只过第 9 节的 20 条，不要看新东西。
2. 每道题按「一句话结论 → 原理 → 工程取舍 → 我的项目」四层展开，**不要一上来就铺陈背景**。
3. 被问到不会的，明确说「这块我没做过，但我会从 X 角度去设计」，然后给出你的思路 — 比硬编或者沉默强得多。

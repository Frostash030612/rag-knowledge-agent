## 二、项目一句话概括

一个面向内部技术文档的问答 Agent。**技术栈刻意保持极简**：零第三方依赖
（除 numpy，连 HTTP 都手写 urllib），全部逻辑在一个文件里，每一层都能解释。

**核心链路**：文档解析 → 切分（500 字/重叠 75）→ 向量化（bge-m3, 1024 维）
→ 索引（向量 + BM25）→ **两阶段检索**（宽召回 40 → 加权分数融合重排取 3）
→ 生成（强制引用 + 结构化输出 + 三层校验 + 回退重修）。

## 三、这个项目最值得讲的一件事：一次完整的优化闭环

这是它区别于「我做了个 RAG」的地方——**用数据把优化方向定下来，再验证**。

**第 1 步 · 发现**：混合检索的 Recall@3 只有 0.8387，不算好。

**第 2 步 · 定位**：没有急着换算法，而是固定检索方式、只把 Top-k 往上加：

| Top-k | 1 | 3 | 5 | 8 | 10 |
| --- | --- | --- | --- | --- | --- |
| Recall | 0.581 | 0.839 | 0.968 | **1.000** | 1.000 |

Top-8 时 Recall 达到 1.0，说明**漏掉的答案全都在候选里，只是没排进前三**
——瓶颈是「召回深度」，不是「检索能力」。

**第 3 步 · 改进**：两阶段检索——向量 Top-40 ∪ BM25 Top-40 宽召回
→ 加权分数融合重排 → 取 Top-3。

| 重排策略 | Recall@3 |
| --- | --- |
| baseline（RRF 排名融合） | 0.8387 |
| **max（分数归一化加权，α=0.7）** | **0.8710** |

关键洞察：**RRF 只用排名信息，区分不了「第 1 名远超第 2 名」**；
换成保留分数落差的加权融合后命中率上升。

**第 4 步 · 验证**：在全量评测集上调参会高估效果，所以做了 5 折交叉验证
（训练折选 α、留出折评估）。**五个折独立收敛到 α=0.7**，无偏提升 **+0.0323**。

**第 5 步 · 诚实收口**：提升只多命中 1 条（26/31 → 27/31），
**在 31 条样本上不具统计显著性**。我不主张这是显著改进，
但它修掉了一个用户可感知的失败——端到端该答则答率从 0.9677 回到 1.0000。

## 五、怎么快速上手

```bash
cd demo
cp .env.example .env          # 填 LLM_API_KEY（模板里有五家平台的配法）
python kb_agent.py ingest --docs docs --index index
python kb_agent.py ask --index index --q "ALM-1042 报警怎么处理？" --show-context
python kb_agent.py compare --index index --set eval/eval_set.jsonl --retrieval-only
python kb_agent.py eval --index index --set eval/eval_set.jsonl --out eval/report.json
```

**没有 API key 也能跑通流程**：加 `--hash-embed` 用离线词袋表示
（语义能力弱，但链路完整、不花钱）。

> **注意**：`.env` 没有被复制（原文件含真实密钥）。请从 `.env.example` 自己建一份。

## 七、已知局限（我主动声明，也写在报告第九章）

1. **语料仍偏小**：47 个 chunk，指标可用于方案间横向对比，不足以推断线上表现。
2. **示例文档非真实业务文档**：内容基于公开的半导体制造与数据分析常识构建。
   **DRAM 领域不存在公开的产线工艺文档**，这是一个应当如实说明的事实。
3. **评测集自建**：38 条由我编写，未与业务方对齐，存在迎合已知能力的偏差。
4. **缺忠实度指标**：只校验「有没有引用」，没校验「引用是否真支持结论」。
5. **延迟未达标**：根因是提示词没有约束输出长度。
6. **重排提升不显著**：+0.0323 只多命中 1 条，需更大评测集才能确认。
7. **术语表污染主索引**：13 个碎片 chunk 在 4 条检索失败中占了 3 条的 Top-3 名额。

# 文档知识库 Agent（kb_agent）

一个用于演示「LLM 应用开发 + Agent 评测」全链路的可运行 Demo。
面向内部技术文档/设备手册的问答场景。

> **注意：** 本仓库的 `docs/` 目录里是**我编写的示例文档**，不是任何公司的真实工艺文档。
> DRAM 领域不存在公开的产线工艺文档——这是一个应当如实说明的事实。
> 把这里换成任何真实的内部文档（产品手册、维修记录、SOP）即可直接使用。

---

## 1. 它能做什么

```
文档 → 切分 → 向量索引 ┐
                       ├→ 混合检索（向量 + BM25 + RRF）→ 重排 → 
文档 → 切词 → BM25 索引 ┘                          ↓
                                     LLM 生成（强制引用 + 结构化输出 + 失败重修）
                                                   ↓
                                     评测数据集 → 指标报告
```

四条命令：

| 命令 | 作用 |
| --- | --- |
| `ingest` | 解析文档、切分、建向量索引与倒排索引 |
| `ask` | 提一个问题，输出带引用的结构化答案 |
| `eval` | 跑评测集，输出检索层 + 生成层指标报告 |
| `compare` | 对比 vector / bm25 / hybrid 三种检索的优劣 |

## 2. 快速开始

### 2.1 配置 API key（最省事的方式：`.env` 文件）

```powershell
# 1) 复制模板（.env.example 里有 OpenAI / DeepSeek / 通义 / 智谱 / 本地 五种配法）
Copy-Item .env.example .env

# 2) 打开 .env，把这一行填上你的 key：LLM_API_KEY=sk-...
notepad .env
```

脚本启动时会**自动加载同目录的 `.env`**（零依赖实现，见 `load_dotenv()`），
所以不用每次开新终端都重设环境变量。

> **安全提示**：`.env` 已在 `.gitignore` 里排除，不会被提交。
> 永远不要把 key 写进代码或 README。
> 真实环境变量优先级高于 `.env`，想临时覆盖时直接 `$env:LLM_API_KEY="sk-..."` 即可。

### 2.2 建索引、提问、评测

```powershell
# 建索引（用 API 做真实 embedding）
python kb_agent.py ingest --docs docs --index index

# 问一句
python kb_agent.py ask --index index --q "ALM-1042 报警怎么处理？" --show-context

# 评测：先只跑检索层，不花额度
python kb_agent.py compare --index index --set eval/eval_set.jsonl --retrieval-only

# 完整评测（含生成层指标，会消耗 token）
python kb_agent.py eval --index index --set eval/eval_set.jsonl --out eval/report.json
```

### 2.3 没有 key 也能先跑通流程

```powershell
# 方式一：命令行加开关
python kb_agent.py --hash-embed ingest --docs docs --index index

# 方式二：在 .env 里打开 USE_HASH_EMBED=1
```

**没配 key 时的行为是刻意设计的**：`ingest` 给出明确的两条路径提示而不是抛异常，
`eval` 自动降级为只跑检索层指标——不用 key 也不该让人卡在第一步。

> **重要**：索引里记录了用的是哪种 embedding。换了 embedding 方式**必须重新 ingest**，
> 否则查询向量和库里向量不在同一空间，检索结果会是垃圾。

## 3. 关键设计与取舍（面试重点，每条都准备被追问）

### 3.1 零第三方依赖
标准库 + numpy。不引 `openai` / `requests` / `rank_bm25` / 向量库。
**理由**：交付摩擦最小，任何机器 clone 下来配好 key 就能跑；
而且自实现 BM25 与 RRF 意味着每一步都能解释内部在算什么——
面试官问公式时不会出现「框架帮我做了」这种答不上来的情况。

### 3.2 混合检索：向量 + BM25 + RRF
- **向量**擅长语义泛化（"怎么处理压力报警" 能匹配到 "腔体压力异常"）
- **BM25**擅长精确匹配（`ALM-1042`、型号、错误码），纯向量容易把这类 token 糊掉
- **用 RRF（Reciprocal Rank Fusion）而不是加权求和**：不同检索器的分数量纲不可比，
  用排名倒数融合更稳，而且**免去了调权重这件事**——

  `score(d) = Σ_i 1 / (k + rank_i(d))`，默认 `k=60`

### 3.3 切分：结构优先 + 重叠
按空行分段聚合成目标长度（默认 500 字符，重叠 75）。
**表格单独处理**：docx 里把表格行拼成 `列1 | 列2` 的文本再入库，
否则表格内容在向量空间里几乎检索不到（这是 RAG 最常见的一个坑）。

### 3.4 生成侧：强制引用 + 结构化输出 + 失败重修
- 系统提示要求每条结论标注 `[1]` 形式的来源编号
- 强制输出 JSON（`answerable` / `answer` / `citations` / `missing`）
- **拿到输出后做三层校验**：能否解析 → 字段类型是否正确 →
  `answerable=true` 时是否真的带了引用
- **校验失败不直接报错**，而是把具体的错误信息喂回模型让它改（最多 2 次），
  仍失败则降级为「结构化输出校验失败」而不是崩溃

  这是对应 JD 里「结构化输出约束、校验及回退重修机制」的实现。

### 3.5 评测与主程序解耦
`eval` 独立读 JSONL 评测集、独立输出 JSON 报告，可以直接进 CI。
**没有 API key 时自动降级为只跑检索层指标**，不阻塞流程。

## 4. 评测指标体系

### 检索层
| 指标 | 含义 |
| --- | --- |
| Recall@k | Top-k 里是否命中正确文档（**本项目的核心指标**） |
| MRR | 平均倒数排名，衡量正确结果排得靠不靠前 |

### 生成层
| 指标 | 含义 | 为什么重要 |
| --- | --- | --- |
| json_valid_rate | 结构化输出一次通过率 | 反映输出可控性（工程可用性） |
| answerable_accuracy | 该答的时候答了 | 漏答率 |
| **false_answer_rate_on_unanswerable** | **资料不足时仍然编答案的比例** | **幻觉率，本套评测最重要的指标** |
| avg_repairs | 平均重修次数 | 反映提示词与校验规则的质量 |
| p95_latency_s | P95 延迟 | 反映可用性 |

评测集 `eval/eval_set.jsonl` 里刻意包含 **3 条「资料中无答案」的问题**
（例如询问不存在的报警码 `ALM-9999`），专门用来测幻觉。

## 5. 实测结果与解读（真实跑出来的，不是编的）

> 完整报告见 **`eval/评测报告_RAG知识库Agent.docx`**（含结论摘要、指标定义、
> 失败分析、延迟拆解、改进路线、逐条结果、复现方式与已知局限声明）。
> 下面只摘最关键的部分。

**语料**：12 个文档 / **47 个 chunk** ｜ **评测集**：**38 条**（31 可回答 + 7 不可回答）
｜ **Top-k = 3** ｜ **模型**：`BAAI/bge-m3`（embedding）+ `Qwen/Qwen3-8B`（生成）

> 说明：本 README 早期版本只有 6 个 chunk / 9 条评测集，当时三种检索模式无法区分。
> 扩充语料后混合检索的价值才显现出来——这本身就是一个结论：**评测集的规模决定能不能得出有效结论**。

### 5.1 检索层：三种模式的对比

| 检索模式 | Recall@3 | MRR@3 | Recall@1 |
| --- | --- | --- | --- |
| vector（纯向量） | 0.8065 | **0.6989** | **0.6129** |
| bm25（纯关键词） | 0.7419 | 0.5699 | 0.4516 |
| hybrid（RRF 融合，原基线） | 0.8387 | 0.6935 | 0.5806 |
| **两阶段检索（宽召回 + 重排）** | **0.8710** | 0.6935 | — |

**分类别看，增益来自哪里：**

| 类别 | vector | bm25 | hybrid |
| --- | --- | --- | --- |
| A 精确匹配（9 条） | 0.889 | 0.889 | 0.889 |
| **B 语义泛化（10 条）** | 0.600 | 0.600 | **0.700** |
| C 跨条聚合（12 条） | **0.917** | 0.750 | **0.917** |

**最有价值的发现——召回深度实验：**

| Top-k | 1 | 3 | 5 | 8 | 10 |
| --- | --- | --- | --- | --- | --- |
| Recall | 0.581 | 0.839 | **0.968** | **1.000** | 1.000 |

### 5.1b 据此做的改进：两阶段检索（Recall@3 0.8387 → 0.8710）

按上表结论，把检索拆成两阶段：**宽召回**（向量 Top-40 ∪ BM25 Top-40 并集）
→ **加权分数融合重排** → 取 Top-3 送入生成。

| 重排策略 | Recall@3 |
| --- | --- |
| baseline（RRF 排名融合） | 0.8387 |
| rrf_pooled（池内 RRF） | 0.8387 |
| **max（分数按最大值归一化后加权，α=0.7）** | **0.8710** |
| minmax / lex | 0.8710 |

**关键洞察**：RRF 只用排名信息，无法区分「第 1 名远超第 2 名」；
改用**保留分数落差**的加权融合后命中率上升。三种加权方式结果相同，
说明起作用的是「用了分数落差」而非具体归一化方式。

**用 5 折交叉验证验证提升（重要）**：在训练折选 α、留出折评估，
**五个折全部独立收敛到 α=0.7**，无偏提升 **+0.0323**。

> **必须诚实说的**：提升只有 1 条样本（26→27），在 31 条上**不具统计显著性**。
> 我主张的是「方向正确且可复现」，不是「显著提升」。
> 但它修复了唯一那个用户可感知的失败（DPPM 问题），
> 端到端**该答则答率从 0.9677 回到 1.0000**。

复现：
```powershell
python kb_agent.py --rerank off compare --index index --set eval/eval_set.jsonl --top-k 3 --retrieval-only
python kb_agent.py --rerank max --alpha 0.7 compare --index index --set eval/eval_set.jsonl --top-k 3 --retrieval-only
```

### 5.2 生成层

| 指标 | 值 | 说明 |
| --- | --- | --- |
| `json_valid_rate` | **1.0** | 结构化输出一次通过率 100%，无需任何回退重修 |
| `answerable_accuracy` | 0.9677 | 31 条可回答题中 30 条作答（1 条因检索漏召而拒答） |
| **`false_answer_rate_on_unanswerable`** | **0.0** | **幻觉率 0**：7 条资料里没有答案的问题全部拒答 |
| `avg_repairs` | 0.0 | 平均重修 0 次 |
| `p95_latency_s` | 65.35 | 延迟中位 22.3s、最大 163.8s（**未达标**，见下） |

### 5.3 怎么解读（这才是面试时要讲的部分）

**① 混合检索的价值被证实了，但只在语义泛化类显现。**
hybrid 的 Recall@3（0.8387）优于纯向量（0.8065）和纯关键词（0.7419）。
但拆到类别上看，**增益全部来自 B 类（语义泛化，0.600→0.700）**；
A 类（精确匹配）三种模式完全相同——**我原本预期 BM25 在编码类查询上占优，实测没有出现**，
这个预期偏差本身值得讲。

**② 真正的瓶颈是「召回深度」，不是「检索能力」。**
这是本轮最有价值的发现：Recall 从 Top-3 的 0.839 升到 **Top-8 的 1.000**，
5 条漏检里 4 条的正确答案就排在**第 4–5 名**。
所以正确的改进动作不是换检索算法，而是**「Top-10 召回 + cross-encoder 重排取 3」**——
按实验推算能把进入生成的命中率从 0.839 提到接近 0.97。

面试话术：**「我没有去比较哪种检索算法更好，而是先问『漏掉的答案到底排在第几』。
结果发现答案基本都在第 4、5 名——这说明该加大召回深度再重排，
而不是换算法。这是一个用数据把优化方向定下来的例子。」**

**③ 幻觉率仍然是 0，而且语料翻 8 倍后更可信。**
7 条不可回答题覆盖了知识库中确实不存在的各类信息（设备型号、财务数据、报警编码、
能耗数值、跨公司对比、良率数字、波长参数），全部拒答。这是**设计出来的结果**，
不是碰巧：系统提示强制「无依据即拒答」、校验规则要求「`answerable=true` 必须带引用」、
评测集主动构造边界样本。

**④ 延迟严重恶化，从 23s 涨到 65s。**
原因是**提示词没有对答案长度做任何约束**——最长答案 241 字耗时 37s，
而 163.8s 的样本输出显著更长。**首先要做的是限制输出长度**，成本最低收益最大。

**⑤ 我修正了自己的标注错误（这个要主动讲）。**
扩评测集时发现：`DPPM` 的答案我标错了 chunk（标成了讲冗余分析的相邻 chunk），
导致该题**恒不命中、且生成侧拒答**。另外术语表使同一术语出现在多个 chunk，
而我只标了其中一个，这会**系统性低估 MRR**。
修正后 hybrid 的 Recall@3 从 0.8065 升到 0.8387。
我为此在构建脚本里加了一道自动校验：**gold chunk 必须包含问题中的关键实体**。

面试话术：**「评测最大的风险不是模型不准，而是标注错了没人发现——
它不报错，只会让指标静默偏低。所以我给评测集加了自动校验。」**

### 5.4 我主动承认的评测局限（面试时说出来是加分）

- **语料太小（6 chunk）**，所有检索指标都不可信，只验证了链路能通。
- **评测集只有 9 条**，且是我自己造的——真实业务里应该由业务方提供场景清单。
- **缺少人工基线**：没有人工标注的「参考答案质量」评分，
  所以生成层只能测「有没有答」，测不了「答得好不好」。
- **没有忠实度（faithfulness）指标**：目前只校验了「有没有引用」，
  没有校验「引用是否真的支持该结论」。
